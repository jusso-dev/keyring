# Integration design

Every call Keyring makes to another service, and the one inbound call it accepts without a session, is listed here with a stable number. The table covers every outbound call in `src/azure/`, `src/notify/`, `src/audit/sink.rs` and `src/auth/`. New flows are added at the end with the next number.

All outbound calls use the one HTTP client in `src/http.rs`: rustls with the `ring` provider, the operating system's roots (or `SSL_CERT_FILE`), 10 second connect and 30 second total timeouts, no redirects, HTTPS only except to localhost. The managed identity's local token service has its own plain HTTP client, limited at start to `localhost`, `127.0.0.1` or `169.254.0.0/16`, and never sent through a proxy.

**Identity column.** *Person (OBO)* means a token Keyring got for the signed-in person through the on-behalf-of exchange; Key Vault, ARM, Log Analytics or Microsoft Graph decides with that person's roles and consent. *Keyring's identity* means its one user-assigned managed identity. *Keyring's credential* means the client secret or the federated credential, used only to authenticate Keyring to Entra on the person's behalf.

## Notes on the flows

- **I-05 is the heart of the design.** There is no client-credentials grant, app-only token or managed identity anywhere in the path that reads or changes a person's Azure data, sharing's role assignments (I-29, I-30) included. Keyring's credential only authenticates the code exchange, the refresh and the OBO request.
- **I-07 has three uses and one identity.** `auth::assertion::ManagedIdentityTokens` takes the audience and caches per audience, so the federated credential, the audit sink and email share one source. Keyring refuses to start with the audit sink or email set and no managed identity, and there is no fallback to a secret or key.
- **I-23 is read as the person on purpose.** Keyring's identity can only write rows through the data collection rule. Reading as it would show people rows they have no right to see.
- **I-26 is the one route without a session.** It checks an Entra token before anything else is read (section 8.1, C15) and reads no vault: everything in the email comes from the event, after checks.
- **I-28 to I-30 exist only with `KEYRING_SHARING=true`.** Off by default; off, every sharing route answers "not found" before anything runs, and Keyring asks Entra for no Graph token. The role (Key Vault Secrets User, `4633458b-17de-408a-b874-0445c86b69e6`) is fixed in code, the scope is built only from the vault's resource ID as Resource Graph returned it and a checked secret name, and the recipient is confirmed through I-28 before I-29 or I-30 is sent. Keyring's managed identity makes no assignment.
- **I-31 is read-only and as the person.** Keyring never changes a Defender alert or plan, and someone without Security Reader (or Reader) on a subscription sees its plan as Unknown and its alerts as not read, not as none.
- **Not called.** Keyring has no application permission, makes no Microsoft Graph call outside sharing, and never calls Key Vault key export, backup, release, decrypt, unwrap or sign. It never reads its own config vault: the platform resolves those Key Vault references at start.

## Notification diagram

The identity side is drawn in chapter 7. The notification flows are drawn here: I-26 in, every email out through I-25, and the triggers in between.

::: wide
![Notification flows. Event Grid delivers Key Vault's expiry events to the webhook; health notices come from a timer and the audit observer; access requests come from a form; activity emails come from a second audit observer; share notices come from a share. All go through one sender and leave through Azure Communication Services as Keyring's managed identity.](../diagrams/drawio/export/04-notification-flows.png)

| Notice | Type in `KEYRING_NOTIFY_TYPES` | Raised by | Recipients | Status |
|---|---|---|---|---|
| Expiry | `expiry` | I-26, Event Grid | `KEYRING_NOTIFY_ADMINS`, or the subscription's `keyring-notify` header held to `KEYRING_NOTIFY_ALLOWED_DOMAINS` | Built |
| Audit sink failing and recovered | `health` | Timer, every 30 s | `KEYRING_NOTIFY_ADMINS` only | Built |
| Refusal burst | `health` | Audit observer and timer | `KEYRING_NOTIFY_ADMINS` only | Built |
| Client secret expiry | `health` | Timer, from `KEYRING_CLIENT_SECRET_EXPIRES` | `KEYRING_NOTIFY_ADMINS` only | Built |
| Access request | `access-requests` | The Request access form (`access.request`) | The vault's `keyring-owners` held to `KEYRING_NOTIFY_ALLOWED_DOMAINS`, or `KEYRING_NOTIFY_ADMINS`; a separate copy, with its own wording and no links, to the requester's sign-in name | Built |
| Watched read | `watched-reads` | A successful `secret.reveal`, `certificate.download_private_key`, `secret.copy.read` or `secret.rollback` | The item's `notify` addresses, and its `owner` with `KEYRING_NOTIFY_OWNER_ON_READ=true`. At most 4 an hour per item | Built |
| Delete, purge or bulk change | `destructive` | A successful delete or purge, or a bulk change that changed at least one item (one email per request, up to 50 names) | The vault's `keyring-owners`, or `KEYRING_NOTIFY_ADMINS` | Built |
| Role use | `role-use` | `role.activate` once the role is on, and `role.deactivate` | The vault's `keyring-owners`, or `KEYRING_NOTIFY_ADMINS`; the admins as well when the role is at a scope above the vault | Built |
| Secret shared | `shares` | A successful `share.grant` (none while a PIM request waits for approval) | The recipient's Graph `mail` (groups get none) and a receipt to the sharer | Built (pull request #289) |

The person who acted isn't sent an activity email about their own action unless nobody else is left. The watched-read, delete and role-use emails are raised by a second audit observer from the request's own successful event, so they work with the audit sink off and can't trigger more email. The vault owners read for them runs as the signed-in person, after the request has answered, in a task with a 10 second limit.
