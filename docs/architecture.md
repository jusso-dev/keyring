# Architecture

Keyring is a stateless web app. It holds a session for the signed-in person and nothing else.

## Principles

- **Act as the user.** Every Azure call that reads or changes a person's data uses a token obtained through the on-behalf-of (OBO) flow. Keyring has no identity of its own with data-plane or control-plane access to anyone's vaults, subscriptions or workspaces. Its one managed identity only proves Keyring is the app, writes audit rows and sends email; it never reads them (see [Who makes each call](#who-makes-each-call)).
- **Store nothing.** No database. Secret values pass through memory on the way to the browser and are never logged, cached or written to disk. The only list Keyring keeps is the names and properties of each vault's items, in the session's memory, for a minute (see [Search](#search)), and the person's own permissions at each scope for five minutes (see [Permission hints](#permission-hints)). Pinned and recently opened items are kept by the person's own browser, not by Keyring (see [Pinned and recently opened](#pinned-and-recently-opened)).
- **Let Key Vault decide.** Authorisation is Key Vault RBAC (or access policies on older vaults). Keyring shows what Azure allows and explains clearly when it doesn't. Disabled buttons ([Permission hints](#permission-hints)) are only a hint; Key Vault still answers every request.
- **Safe by default.** Purge is off. Deletes need typed confirmation. Secret values are hidden until revealed, and Keyring tries to clear the clipboard after a copy.

## Request flow

1. The browser signs in with Entra ID using OIDC (authorisation code flow with PKCE).
2. The server keeps the user's tokens in a server-side memory session. The browser only holds a random session ID. Nothing is persisted.
3. For each Azure call, the server exchanges the user's token via OBO for a token scoped to:
   - `https://vault.azure.net/.default` for Key Vault data plane
   - `https://management.azure.com/.default` for ARM and Resource Graph
   - `https://api.loganalytics.io/.default` for Log Analytics (the audit view)
4. Results go back to the browser. Errors from Azure (403, 404, throttling) are mapped to plain-English messages.

Keyring works with the Azure public cloud only: these hosts, `login.microsoftonline.com` and `<vault>.vault.azure.net` are fixed in the code. Sovereign clouds and managed HSM aren't supported.

## Components

| Part | Job |
| --- | --- |
| Web server | Axum on Tokio. Routes for vaults, secrets, certificates, keys, expiry and age, generator, audit and access |
| Pages | Askama templates compiled into the binary. Plain hand-written CSS |
| Browser script | One small hand-written vanilla JS file for copy to clipboard, clearing it again, and similar extras. Pages work without it |
| Sign-in | `openidconnect` crate, authorisation code flow with PKCE |
| Azure calls | `reqwest` with rustls, calling the Key Vault, Resource Graph, ARM and Log Analytics REST APIs directly. No `azure_*` crates (see below) |
| Sessions | In-memory store keyed by a random cookie. Nothing persisted |

## Stack and why

Keyring is Rust so the dependency tree stays small and auditable. Next.js and the npm ecosystem were ruled out: a typical app pulls in hundreds of packages, many with install scripts, and that's a lot of trust to extend for a tool that handles secrets.

Rules for the codebase:

- No npm, no Node toolchain, no bundler, no CDN scripts, no Tailwind.
- Server-rendered HTML first. JavaScript is an optional extra, hand-written and served from the same origin under a strict CSP.
- No `unsafe` code in the crate (`forbid` lint).

## Code layout

| Path | What's in it |
| --- | --- |
| `src/main.rs` | Start-up: load config, start logging, bind and serve |
| `src/lib.rs` | `AppState` and the router, so tests can drive the app without a socket |
| `src/config.rs` | Typed config from environment variables. Fails fast with a list of what's missing |
| `src/secret.rs` | `Secret`, a string wrapper whose `Debug` and `Display` print `[redacted]` |
| `src/description.rs` | The rules for the note kept in the `description` tag |
| `src/routes/` | Axum handlers, one file per area |
| `src/auth/` | Sign-in and sessions |
| `src/azure/` | On-behalf-of exchange and REST clients for Azure |
| `src/notify/` | Email through Azure Communication Services, as Keyring's managed identity |
| `templates/` | Askama templates, compiled into the binary |
| `static/` | Hand-written CSS and one small JS file, embedded in the binary with `include_str!` |

Static files are compiled in rather than read from disk, so the container needs no writable or readable app directory and nothing can be swapped at run time.

Logging uses `tracing` on standard output, as `key=value` text or, with `KEYRING_LOG_FORMAT=json`, one JSON object per line (a small formatter in `src/telemetry.rs`). Two kinds of line are written:

- one per request, `request method=GET path=/secrets status=200 ms=12`. The path never has the query string. Requests that end in a 5xx are logged at `warn`, the rest at `info`.
- one of Keyring's own **audit events** for each audited request (below). With the audit sink on, each event is also sent to Log Analytics ([The audit sink](#the-audit-sink)).

Request and response bodies, headers, query strings, secret values, tokens and Azure's error messages are never logged. Vault and item names do appear. `KEYRING_LOG_LEVEL` is checked at start against `error`, `warn`, `info`, `debug` and `trace`; `off` and filter strings are refused. Audit events are written at every level. Where the lines end up on each host is in [deploy.md](deploy.md#logs).

### Keyring's own audit events

Key Vault's audit log (the Audit section below) records every call Key Vault receives, but sees Keyring's outbound address, not the browser's, and nothing Keyring refuses before calling it. Keyring's own audit events, in `src/audit/mod.rs`, fill that in. The schema (version 1) and example queries are in [deploy.md](deploy.md#audit-event-fields).

- **One way out.** Every event is an `AuditEvent` written by `audit::record`. A test fails if any source file writes its own `tracing::...!(subject = ...)` action line.
- **One event per request.** `audit::layer` sits outside the time limit, the origin check and the session check, and holds a draft for the request in a task-local. The router marks each audited POST with `audited(Action, handler)`. Guards add a refusal reason (form token, typed name, purge off, managed item, cross-site, no session, no reason), the session check adds who, the vault and name checks add what, and `AzureClient::send` adds any Azure failure (status and code, never the message). When the request finishes, the layer writes one event if an action was set. The first refusal wins; otherwise a 2xx or 3xx is `success`, then the last Azure failure, then the status. A request dropped before it answers, such as when the browser closes the connection, still gets its event, as `failed` with `cancelled`. So a route can't finish without its event, whatever path it took.
- **Coverage is tested.** `tests/audit_events.rs` reads every POST route from `src/routes/mod.rs`. Each must be `audited(...)` or on an exempt list with a reason (choosing a vault, the generator, the certificate upload and secrets import previews and cancels, redirects of old addresses: none of them write to or read values from Key Vault). It then posts a forged token to every audited route and checks for exactly one `refused` event, with nothing reaching Key Vault.
- **Reasons** (optional, `KEYRING_REQUIRE_REASON` and `KEYRING_REASON_TICKET_PATTERN`, both checked at start, the pattern compiled once with the `regex` crate, which matches in linear time, and a small size limit). `audited(...)` runs one gate, `routes::reason::gate`, before every audited handler, so no handler checks a reason itself. For an action that needs one (`reveal`: a reveal, a copy to another vault or a private key download; `all`: every action on an item) it reads the URL-encoded form under the route's body limit. If the form token is wrong, step-up isn't met or purge is off, it steps aside and the handler refuses as before, so the order stays form token, step-up, reason, all before any Key Vault call. Otherwise it cleans the reason (`src/reason.rs`: control and invisible formatting characters become a space, 5 to 200 characters) and checks the ticket against the anchored pattern. A good reason goes on the event as `reason` and `ticket`. A missing or bad one is refused with `reason_required` and a page that asks for it and posts the same fields again, except a secret value, which is never written back into a page. The reason never goes in an address, so a step-up round trip asks for it again. Key Vault doesn't know about it: the CLI needs no reason. It's for audit, not a hard control. The gate fails closed: it takes the vault and item from the route's decoded parameters, the same ones the handler reads, so a percent-encoded address is checked like the plain one, and a request it can't place (no session, no valid vault name) is refused with `invalid_request` rather than passed on.
- **Joining to Key Vault's log.** Each Key Vault call carries a new UUID as `x-ms-client-request-id`; the event's `kv_request_id` is the last one sent for the request.
- **Who and from where.** `actor_oid`, `actor_tid` and `actor_upn` come from the verified ID token. `session_ref` is an HMAC of the session ID with a key derived from `SESSION_SECRET`, so a session's events join up without the cookie value in the log. `client_ip` is the socket peer unless `KEYRING_TRUSTED_PROXY_HOPS` is set, when it is that many entries from the right of `X-Forwarded-For`. Too high a value lets a browser choose its address, so the default is 0.
- **Many items in one request.** A secrets import writes many secrets in one request. The request gets its one `secret.import` event as usual (`success`, or `failed` or `denied` with `partly_written` or `none_written`), and each secret written gets its own `secret.import` event with its name, its own outcome and `kv_request_id`, and the same person, session and browser, through `audit::ItemEvents`. A bulk change (`secret.bulk_update`, `certificate.bulk_update`, `key.bulk_update`) works the same way, with `partly_changed` or `none_changed`. If the request is cut off part way, each item already sent still gets its event (`cancelled` for one in flight), and an item never sent gets none. With `KEYRING_REQUIRE_REASON=all`, the import preview and the bulk change review ask for the reason and it is repeated on each of those events.
- **Outside a request.** Session expiry found by the sweep is recorded directly, with no browser details. Read-only pages write no event; the request line covers them.

### The audit sink

Optional (`KEYRING_AUDIT_INGESTION_ENDPOINT`, `KEYRING_AUDIT_DCR_ID`, `KEYRING_AUDIT_STREAM`). `src/audit/sink.rs` sends Keyring's own audit events to a custom table, `KeyringAudit_CL`, through the Azure Monitor Logs Ingestion API. It is not Key Vault's audit log, which the audit pages read as the person.

- **One hook.** `audit::record` writes the event to standard output, as always, then queues it for the sink. The actor was filled in from the verified session when the event was made. The sender never looks up or guesses an actor.
- **Written as Keyring's managed identity only.** Every ingestion call carries a token for `https://monitor.azure.com` from the one configured managed identity, from the same token source as the federated credential. Keyring refuses to start with the sink set and no managed identity. There is no client secret or second identity fallback, and no path sends a person's token to the ingestion endpoint (a test fails if one does). Each row has writer columns (`WriterIdentityClientId`, `KeyringInstance`, `KeyringVersion`) next to the actor columns.
- **One column list.** `sink::COLUMNS` is the table's schema. A test checks `infra/modules/audit-sink.bicep` and the schema version 1 field names against it.
- **Schema version.** Adding an optional field (left out of the event when not set) keeps the version; renaming or removing a field, or changing its meaning or type, is a new version. `tests/audit_events.rs` pins the field names version 1 shipped with, lists the ones added since, fails on a field in neither list, and checks each added field's column is read with `column_ifexists` in the Sentinel parser. See [deploy.md](deploy.md#audit-event-fields).
- **Batching and failure.** A bounded queue (10,000 events, oldest dropped and counted when full) and one sender task that flushes every 5 seconds or at 500 events, gzipped, under the 1 MB a call limit. 429 and 5xx are retried with backoff and `Retry-After`; a 401 or 403 drops the cached token and retries; any other 4xx or a redirect drops the batch and counts it. The ingestion client is the main HTTPS-only client: no redirects, no plain HTTP.
- **Health.** The sink is degraded once it has failed for a minute with no success. `/healthz/audit` (no sign-in) shows `ok`, `degraded` or `off` and counts, with a 503 while degraded. `KEYRING_AUDIT_REQUIRED=true` refuses reveals and private key downloads while degraded, before Key Vault is called.
- **Shutdown.** After the server stops taking requests, `main` sends what is left for up to 10 seconds. Anything still queued is counted and was already on standard output.
- **Background job.** The sender is a background task, but it holds no stored credential (it asks the platform's local token service for a short-lived token each time the cached one runs low) and only handles audit fields, which "The app itself never runs background jobs with stored credentials" (see [Alerts](#alerts)) still allows.

### Email

Optional (`KEYRING_NOTIFY_*`, all checked at start). `src/notify/` sends email notices through Azure Communication Services. It is the sender only: each kind of notice builds a `notify::Notification` (a type, `to` addresses, an optional item and template data) and calls `Notifier::enqueue`, which returns at once with `Queued`, `QueueFull`, `Off`, `NoRecipients` or `Invalid` and never fails the request that raised it. `notify::Notice` and `templates/notify/notice.{txt,html}` are the one built-in template pair.

- **Sent as Keyring's managed identity only.** Every call carries a token for `https://communication.azure.com` from the same token source as the federated credential and the audit sink. Keyring refuses to start with `KEYRING_NOTIFY_ACS_ENDPOINT` set and no managed identity. No access key, connection string, SMTP password or second identity.
- **Endpoint and poll address.** The endpoint must be `https://<resource>[.<geography>].communication.azure.com` with no port, user name, path, query or fragment. ACS's `Operation-Location` is only fetched with the token if it is on the same scheme, host and port, under `/emails/operations/`; otherwise the email is counted as accepted with an unknown result. The client follows no redirects. A test points the poll address at another server and checks it is never called.
- **Recipients.** `to` only. Each address is parsed strictly (one `name@domain`, no display name, quotes, spaces, commas or line breaks), checked against `KEYRING_NOTIFY_ALLOWED_DOMAINS` when set, and held to `KEYRING_NOTIFY_RATE_PER_HOUR` (default 20) per recipient per type. A recipient is counted by mailbox (the local part lower-cased, any `+tag` taken off), so a change of case or a `+tag` shares one limit, and one mailbox is listed once in an email. The rate limit is in memory, a fixed one-hour window, in a map of at most 10,000 pairs: when full, expired pairs are cleared, and if it is still full a new pair is refused, so filling the map can't reset anyone's count.
- **Content.** Subjects are fixed text, the type and, when there is one, the item, whose vault and name have passed Key Vault's naming rules. Free text in a body has control and invisible characters taken out (the same list as reasons), and the HTML part is escaped by Askama. Never a secret value, token, private key, Azure error message or reason text: a test captures every log line at TRACE and every body the mock ACS received and checks.
- **Repeatability.** Each email has one `Repeatability-Request-Id` and `Repeatability-First-Sent`, reused with the same body on every retry. ACS remembers a request for five minutes, so the sender gives up on an email five minutes after its first try (or on a 412), counting it as failed or, if a try may have reached ACS, as maybe sent. It is never retried under a new ID. A 409 is "still in progress" and retried.
- **Delivery.** A bounded queue (1,000) and one sender task. 429, 408 and 5xx retried with backoff and `Retry-After`; 401 and 403 drop the cached token and retry; anything else is dropped and counted. After a 202, the result is polled at most three times. `/healthz/notify` (no sign-in) shows `ok`, `degraded` or `off` and counts, 503 while degraded. On shutdown, queued email is sent for up to 10 seconds before the audit sink's own flush.
- **Audit.** Each email is one `notify.sent` or `notify.failed` event, with `notify_type`, `notify_recipient_count` and the item. Addresses are personal data: they appear nowhere unless `KEYRING_NOTIFY_AUDIT_RECIPIENTS=true`, which puts them on the event, and so in the audit log line on standard output as well as the sink. A failed result's Azure message is never parsed into a string.
- **Background job.** Like the audit sink, the sender holds no stored credential and handles no value.

Release builds unwind on a panic rather than abort, so one request that hits a bug gets a 500 page and every other session carries on. Keyring's own panic hook logs only where the panic happened, never its message, since that can hold request data.

Static files are served from `/static/` with a version in the query string, taken from a hash of the file's contents. A request with the current version is cached for a year (`immutable`), since a new build changes the URL. Without it, or with an old one, the current file comes back with a five-minute cache. HTML pages, reveals, downloads and CSVs are `no-store`.

`unsafe_code` is set to `forbid` in `Cargo.toml` lints, which has the same effect as `#![forbid(unsafe_code)]` on every target in the crate.

## Sign-in and sessions

- `/auth/start` builds the Entra authorise URL with the `openidconnect` crate: authorisation code flow, PKCE (S256), random state and nonce. It asks for `openid profile offline_access` and Keyring's own API scope, so the access token can later be exchanged on behalf of the user.
- State, nonce, PKCE verifier and the return path go in a short-lived (10 minute) cookie, encrypted with AES-256-GCM using a key derived from `SESSION_SECRET` (HKDF-SHA256). The cookie name is bound in as associated data.
- `/auth/callback` checks the state in constant time, swaps the code for tokens and has the crate verify the ID token: signature against the tenant's published keys, issuer, audience, expiry and nonce. An `error=` reply is only acted on when its `state` matches the sign-in in progress.
- Entra's metadata and signing keys are cached for an hour, and concurrent sign-ins share one fetch. If an ID token is signed with a key that isn't in the cache, the cache is marked out of date, the keys are fetched again and the same sign-in is checked once more, so a key rollover doesn't fail anyone. If a fetch fails, the last good copy is kept and Keyring waits 30 seconds before trying again.
- Sessions live in server memory. The browser only gets a random 256-bit ID in an http-only, `SameSite=Lax` cookie (`Secure` and `__Host-` prefixed over HTTPS). Tokens never leave the server. Sessions end after an hour idle or 12 hours in total. A task drops expired sessions, with their tokens, every minute. A restart signs everyone out; running several copies needs sticky sessions.
- Sealed cookies (sign-in state and one-off messages) carry the time they were made, and the server refuses them once they're too old (10 minutes for sign-in, one minute for messages), whatever the browser does with `Max-Age`.
- A form posted after the session ended goes back to sign-in, and then to the form's page, with a message that nothing was saved.
- Every route except sign-in, callback, signed-out, `/healthz` and `/static` sits behind a middleware that requires a session. Without one, GET requests are sent to sign-in with the path remembered. Return paths must be local (`/` but not `//`, no backslashes or control characters).
- Sign-out is a form post with a per-session token. It drops the session here, then sends the browser to Entra's end-session endpoint, which returns to `/auth/signed-out`.
- **Step-up** (optional, `KEYRING_STEP_UP_AUTH_CONTEXT` and `KEYRING_STEP_UP_MAX_AGE`). The callback keeps `acrs` (well-formed context IDs only) and `auth_time` from the verified ID token in the session. One guard, `routes::step_up::require`, runs before a reveal, a private key download, a rollback, a copy to another vault and a purge, on both the confirmation page and the post. If the session's `acrs` lacks the configured context, or `auth_time` is older than the maximum age (or missing), the action stops before any Azure call, its audit event gets `step_up_required`, and the page links to `/auth/start?reason=step_up` with the confirmation step as the return path. That start adds `claims={"id_token":{"acrs":{"essential":true,"value":"cN"}}}` (merged with any claims challenge Entra sent earlier), and `prompt=login` with `max_age` for the age rule. What is asked for comes from settings, never from the request. The sign-in state cookie marks it as a step-up, and a step-up callback whose token still doesn't meet the settings is refused with a plain page and a `step_up_not_met` event: the old session is kept, no new one is made, and the only link is back to the confirmation step, so it can't loop. Conditional Access blocks (AADSTS53000 to 53004) are told apart from "sign in again" in `src/auth/entra.rs`. Later actions that need it (PIM activation) call the same guard.
- `ENTRA_AUTHORITY_HOST` (default `https://login.microsoftonline.com`) exists so tests can point at a mock identity provider. `KEYRING_TEST_MANAGEMENT_URL`, `KEYRING_TEST_KEYVAULT_URL`, `KEYRING_TEST_LOGANALYTICS_URL`, `KEYRING_TEST_AUDIT_INGESTION_URL` and `KEYRING_TEST_NOTIFY_ACS_URL` do the same for ARM, Key Vault, Log Analytics, the audit sink and email. Leave all six unset in real deployments; Keyring logs a warning at start naming any that are set. Plain `http://` is only accepted for localhost.

## On-behalf-of tokens

- `azure::TokenBroker` swaps the user's access token (issued for Keyring's own API scope at sign-in) for a token scoped to Key Vault, ARM or Log Analytics, using the OBO grant (`urn:ietf:params:oauth:grant-type:jwt-bearer`, `requested_token_use=on_behalf_of`).
- If the user's own token has less than five minutes left, the broker refreshes it with the refresh token first, keeping any rotated refresh token.
- Exchanged tokens are cached in the session, in memory, per resource, and reused until five minutes before expiry. Sessions never share tokens.
- Concurrent requests in one session, such as the expiry dashboard reading several vaults at once, share one refresh and one exchange per resource. If that call fails, the requests waiting on it get the same answer instead of each trying in turn. A request that arrives later tries again.
- Entra errors are mapped: `interaction_required` and `login_required` mean sign in again, and so does `invalid_grant` with an Entra error number a fresh sign-in fixes (MFA, conditional access, an expired or revoked refresh token). Any other `invalid_grant`, such as a wrong `ENTRA_API_SCOPE`, is shown as a setting for the admin. `consent_required` and AADSTS 65001, 65004 and 650057 mean an admin must consent. Only the error code is logged, never the description.
- There is no client-credentials grant, managed identity or app-only token in the path that reads or changes anyone's Azure data. Keyring's credential is only used to authenticate the sign-in code exchange, the refresh and the OBO request.
- That credential is either the client secret (`ENTRA_CLIENT_SECRET`) or, when `KEYRING_MANAGED_IDENTITY_CLIENT_ID` is set without a client secret, a short-lived token from a user-assigned managed identity that the app registration trusts as a federated credential. Keyring gets the token from the platform's local token service (`IDENTITY_ENDPOINT`, audience `api://AzureADTokenExchange`) and sends it as `client_assertion`, with `client_assertion_type` `urn:ietf:params:oauth:client-assertion-type:jwt-bearer`, in place of `client_secret`. It never sends both. The token is cached until five minutes before it expires, one fetch at a time, and is held in a `Secret`.
- `auth::assertion::ManagedIdentityTokens` is the one managed identity token source. It takes the resource and keeps a cache per resource, so the federated credential (`api://AzureADTokenExchange`), the audit sink (`https://monitor.azure.com`) and email (`https://communication.azure.com`) share one source and one identity.
- The local token service speaks plain HTTP, so it has its own HTTP client, separate from the HTTPS-only one. Keyring refuses to start unless `IDENTITY_ENDPOINT` is on `localhost`, `127.0.0.1` or `169.254.0.0/16`, so that client can't be pointed at the network.
- Tokens live in `AccessToken` and `Secret` wrappers whose `Debug` and `Display` print `[redacted]`.

### Who makes each call

- **As the person (OBO):** everything that reads or changes Key Vault, Resource Graph, ARM or Log Analytics data on their behalf.
- **As Keyring's managed identity:** proving to Entra that it is the app (the federated credential), writing audit rows (the audit sink) and sending email through Azure Communication Services. Nothing else, and never a client secret or second identity for these.
- **The identity's roles:** reading Keyring's own config secrets, Monitoring Metrics Publisher on the one audit data collection rule, and, with email on, a custom role with `Microsoft.Communication/CommunicationServices/Read` and `Write` on the one Communication Services resource in Keyring's own resource group. No role on any vault or workspace read path.

Keyring has one managed identity for everything it does as itself, set by `KEYRING_MANAGED_IDENTITY_CLIENT_ID`. `KEYRING_FEDERATED_IDENTITY_CLIENT_ID` is a deprecated alias, read for one release; Keyring refuses to start if both are set to different values. **No future feature may add a second identity or a client secret for Keyring's own calls.**

### Plain REST, not the `azure_*` crates

`azure::AzureClient` calls the Key Vault, ARM, Resource Graph and Log Analytics REST APIs directly with `reqwest`. The official Rust SDK crates are still in beta, change often between releases and pull in a large dependency tree of their own, including their own identity and HTTP layers we'd have to work around to plug in OBO tokens. The REST APIs Keyring uses are a handful of stable, versioned endpoints, so a thin typed wrapper is less code to trust. We'll revisit when the SDK reaches a stable 1.0.

The client attaches the user's token to every call. On a 401 it drops the cached token, gets a fresh one and tries once more. Error replies keep the status and Azure's error code, which the UI maps to its own plain-English text.

Azure's own message is shown in one case only: a 400 on a write, under the form it came from, as "Key Vault said:". For a validation failure it is the only thing that names the field and the rule. The forms are certificate create and upload, key create and the key rotation policy. The message is cut to 500 characters and escaped as text, and the form keeps what was typed. It is never logged. It isn't shown on read paths or for 401, 403 and 404, where Keyring's own text is clearer and the message can name items the person can't see.

## HTTP client and TLS

All outbound calls use one `reqwest` client on rustls with the `ring` crypto provider (no OpenSSL, no aws-lc; `deny.toml` bans both). It has connect and total timeouts, does not follow redirects and refuses plain HTTP except to localhost. Errors from the client are logged without URLs or bodies.

- **Trust store.** Server certificates are checked against the operating system's roots (`rustls-platform-verifier`, which on Linux reads them with `rustls-native-certs`). Setting `SSL_CERT_FILE` (or `SSL_CERT_DIR`) replaces the system roots with that file or folder, which is how a private CA is trusted.
- **Proxies.** `HTTPS_PROXY`, `HTTP_PROXY`, `ALL_PROXY` and `NO_PROXY` (and their lower-case forms) are read from the environment, as reqwest does by default. The managed identity's local token service is never reached through a proxy.
- **Inbound proxies.** `X-Forwarded-*` headers are ignored. `APP_BASE_URL` is the only source of Keyring's own origin.

## Supply chain

- `Cargo.lock` committed. Builds use `--locked`.
- Toolchain pinned in `rust-toolchain.toml`.
- `cargo deny check` covers licences (allow-list), advisories, bans and sources (crates.io only). `cargo audit` runs as well. Both run in CI and fail the build.
- Adding a crate needs a reason in the PR. Prefer crates that are widely used, maintained and light on dependencies.
- Dependabot opens weekly, grouped updates for `cargo`, `docker`, `rust-toolchain` and `github-actions`. The Rust toolchain and the Docker images share one pull request, so the builder image and `rust-toolchain.toml` move together. CI also fails if they differ.
- The repository has secret scanning with push protection, Dependabot security updates and CodeQL code scanning turned on, and its Actions settings refuse any action not pinned by SHA.
- GitHub Actions are pinned by full commit SHA. Tools that actions install are pinned by version, with no fallback download. The Bicep CLI is pinned by version and the Dockerfile frontend by digest.
- CI produces two CycloneDX SBOMs as build artifacts: one from `Cargo.lock` listing every crate in the binary (`cargo cyclonedx`), and one for the image's base packages (Syft). An image scan alone can't see the crates, since they're compiled into one stripped binary. The release workflow (`.github/workflows/release.yml`) builds each version tag's image, runs the image checks from CI's `docker` job, and adds a signed build provenance attestation and an SBOM. It pushes to `ghcr.io` only once the repository variable `KEYRING_PUBLISH_IMAGE` is `true`, which it isn't yet. It doesn't rerun the Rust or supply-chain checks. Instead it refuses a tag unless the commit is on `main` and CI's four required checks passed on it. [SECURITY.md](../SECURITY.md#verifying-an-image) shows how to verify an image. If you build and push your own image, add provenance where you build it.

### Dependency policy

What CI checks, on every PR, every push to `main` and weekly:

| Check | Tool | Fails when |
| --- | --- | --- |
| Licences | `cargo deny` | A crate's licence isn't on the allow-list in `deny.toml` (permissive licences only) |
| Advisories | `cargo deny`, `cargo audit` | A crate has a RustSec advisory, is unmaintained or is yanked |
| Bans | `cargo deny` | A banned crate turns up (`openssl`, `native-tls`, `aws-lc-rs`, `aws-lc-sys`) or a dependency uses a `*` version |
| Sources | `cargo deny` | A crate comes from anywhere other than crates.io |
| Lock file | `--locked` | `Cargo.lock` is out of date |

Duplicate versions of the same crate are reported as warnings, not failures, so they show in the CI log for review. There are several today. Trim them when it's easy.

To add a crate:

1. Check you need it. A few lines of our own code often beat a new dependency.
2. Prefer crates that are widely used, actively maintained and pull in little else. Turn off default features and enable only what's used.
3. Run `cargo deny check` and `cargo audit` locally.
4. In the PR, say what the crate is for and what it adds to `Cargo.lock`.

To accept an advisory that doesn't affect Keyring, add its ID to `ignore` in `deny.toml` with a comment saying why, and link an issue to revisit it.

## Container

Built by `Dockerfile` and checked in CI on every change: non-root numeric user, no shell, under 30 MB, and a smoke test with `--read-only --cap-drop ALL --security-opt no-new-privileges` that checks `/healthz` answers without sign-in and `/` redirects to sign-in. Size today is about 8 MB.

- Multi-stage Dockerfile. Builder and runtime images pinned by digest.
- Static musl binary on `gcr.io/distroless/static` (nonroot).
- `VERSION` and `VCS_REF` build arguments set the `org.opencontainers.image.version` and `org.opencontainers.image.revision` labels. CI passes the crate version and commit, and checks the labels.
- Runs as non-root, with a read-only root filesystem and no extra capabilities. No shell in the runtime image.
- `/healthz` for probes.

## Local development

- `cargo run` with a `.env` file, or `docker build` and `docker run --env-file .env --read-only`.
- `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test` must pass before a PR merges. ## Vault discovery

Azure Resource Graph query over every subscription the user can see:

```kusto
resources
| where type =~ 'microsoft.keyvault/vaults'
| project id, name, resourceGroup, subscriptionId, location, properties.enableRbacAuthorization, properties.enableSoftDelete, properties.enablePurgeProtection, properties.publicNetworkAccess, properties.networkAcls.defaultAction, properties.privateEndpointConnections
```

Results are fetched in pages of 1000 (the Resource Graph maximum), following `$skipToken` up to 100 pages. A second query reads subscription names from `resourcecontainers`; if that fails the list still shows, with subscription IDs instead of names. Missing flags take Azure's defaults (soft delete on, RBAC and purge protection off). The network columns are only used by the vault health page.

The list also has an Audit logs column. For the vaults on the page, Keyring reads each vault's diagnostic settings through ARM as the person (Reader), six at a time, 5 seconds each and 10 in all, so the list stays quick. It shows "On" when a setting sends audit logs to a Log Analytics workspace, "On, not in Log Analytics" for a storage account, event hub or partner only, a warning badge "Off" when nothing sends them anywhere (the audit view can't work then), and "Unknown" with the reason when the settings couldn't be read in time.

The list is filtered on the server (name or resource group, subscription, tag as `key` or `key=value`) and shown 200 to a page. The main JavaScript file, `static/app.js`, also filters the visible rows as you type; without it the form submits and the server filters.

The vault is in the address: every secrets, certificates, keys and audit page lives under `/v/{vault}/` (for example `/v/kv-prod/secrets/db-password`), and the vault in the address is the one that request acts on. So a link can be sent to a colleague, and two tabs can hold two vaults. Its name is checked against Key Vault naming rules before it's used or put into a URL, and a name that fails is "not found" without a request leaving Keyring. Keyring doesn't check Resource Graph for that name: Key Vault's own 403 or 404 on the first call covers a vault the person can't see, and the pages handle that with the role to ask for. Seeing a vault in Resource Graph only needs the ARM Reader role, so opening it can still fail with 403 on the data plane.

The session also remembers the vault last used. That is only for the side navigation links, and for the old addresses without a vault (`/secrets/db-password`), which answer with a 308 to the same page under that vault, or ask for a vault if none has been used. Handlers never read it to decide which vault to act on. The audit view keeps the vault's ARM resource ID with it, and only uses that copy when the address names the same vault.

## Secrets

Keyring calls the Key Vault secrets REST API (version 7.5) directly as the user.

- The list uses `GET /secrets`, which returns properties only, in pages of 25 following `nextLink`. A `nextLink` is only followed if it points at the same vault.
- A secret's page reads `GET /secrets/{name}/versions` and shows the newest version. That call never returns values, so opening a page doesn't read the secret.
- Values are only read by the reveal action, by rollback, which copies an older version's value into a new version on the server without showing it, and by copy to another vault.
- **Copy to another vault.** "Copy to another vault" on a secret's page (disabled with the role named when the hints say the person can't read the value) opens `/v/{vault}/secrets/{name}/copy`: the target vault, picked from the vaults the person can see (Resource Graph, as them), the target name (the same by default), and what to bring besides the value: content type, tags, start and expiry dates, enabled, all ticked by default. A passed expiry date isn't brought. The review (`/copy/review`, a GET) names both vaults, says the value isn't shown, and looks at the target name with `GET /secrets/{name}/versions` and `GET /deletedsecrets/{name}` in the target vault: new, a new version of an existing secret, or soft-deleted (stop, recover first). It never reads a value. The post to `/copy` (`audited`, `secret.copy.read`) is guarded like a reveal, in the same order: form token (bound to the source vault in the address), `KEYRING_AUDIT_REQUIRED`, step-up, and the reason gate, which treats it as a reveal. Then, before any Key Vault call, the target vault must pass `is_valid_vault_name` and be in the person's vault list read as them, the target name must pass the object name check, and the target can't be the source. The source must not be a certificate's backing secret and must be enabled; the target name must not be soft-deleted or a certificate's. Then `GET /secrets/{name}` in the source and `PUT /secrets/{name}` in the target, both as the person. The value is held in `Secret` between the two and goes nowhere else: not a page, address, flash message, error page, log line or audit event. If the read fails nothing is written. If the write fails the page says "not copied", with the role to ask for on a 403 or Key Vault's status and code otherwise, never its message. The write gets its own audit event (`secret.copy.write`) on the target vault and name through `audit::ItemEvents`, so a refusal from either vault can be told apart. The target vault isn't the one in the address, so the handler drops its kept list itself, before and after the write. Every page in the flow is `no-store`. Code: `src/routes/secrets/copy.rs`.
- Names from URLs are checked against Key Vault's rules (letters, digits and hyphens, up to 127) and versions must be 32 hex characters, before they go into a request.
- "Expiring soon" means within 30 days. Dates are shown in UTC.
- Editing properties changes the current version. Key Vault can change a version's start and expiry dates but never remove them: it keeps a date sent as `null`. So the edit form refuses a removed date and says to set a new value with the date left blank, which makes a new version without it.
- Filters (name, tag, expired or expiring, disabled) run on the server, with the same filter-as-you-type extra as the vault list.
- **Import.** "Import secrets" on the list reads a `.env` file (`NAME=value`, double or single quotes, `#` comments, `export`) or a CSV with a header row (`name,value`, and optionally `content_type`, `expires`, `tags` as `k=v;k=v` and `description`), up to 500 rows and 1 MB. A UTF-8 BOM and CRLF line ends are accepted. Names are changed to Key Vault's rules (anything but a letter, digit or hyphen becomes a hyphen, so `DB_PASSWORD` becomes `DB-PASSWORD`), and two rows that become the same name, ignoring case, refuse the file. Values are stored exactly as written, including ones that look like spreadsheet formulas: this is input to Key Vault, not a file anyone opens. The preview lists each original and converted name, and whether it is new, a new version of an existing secret, blocked by a deleted secret that can still be recovered, owned by a certificate, or has a problem of its own, with the expiry and tags. It never shows a value. It makes list calls only (`GET /secrets` and `GET /deletedsecrets`). The secrets wait in the server-side session as `Secret`s, zeroised when dropped, until the import, "Start again", opening the form again, the session ending, or 10 minutes. A preview still running when the person starts again isn't kept, and confirming an older preview leaves a newer one waiting. Errors about the file give a line or column number, and quote only names that pass Key Vault's rules, never other text from the file. On import each one is a `PUT /secrets/{name}` as the person, four at a time; no new write starts after 45 seconds and Keyring stops waiting at 70, inside the 90 second request limit, and says so per row: "not sent" for a row whose write never began, "unknown" only for one cut off in flight. The results page lists every row with its outcome, never Azure's message. There is no export: a plain-text file of every value is what a secrets tool should make hard.
- **Bulk changes.** The secrets, certificates and keys lists have a checkbox on each row and a "With selected" form: add or change a tag, remove a tag, set or remove the description, set an expiry date (secrets and keys only; a certificate's dates come from the certificate), enable or disable. Delete and purge are never offered in bulk. The checkboxes join the form through the `form` attribute, so the filter form isn't nested in it and the list works without JavaScript; there is no "select all" control. The first post (`{kind}/-/bulk`) checks the form token, the change and every name (Key Vault's rules, at most 100, repeats dropped), reads the list once, and shows every item with exactly what will happen to it: the change, no change needed, can't change (with why), or not found. Nothing is kept on the server: the names and the change go back in hidden fields, and the second post (`{kind}/-/bulk/apply`, `audited`) checks all of it again. Disable needs the number of items typed, the way delete needs the name. Each item is then read and changed as the person, four at a time, with the same deadlines as an import, and the results page says per item: done, no change needed, refused by Keyring (managed by a certificate, or at Key Vault's 15 tags), refused by Azure (with the role the hints code names), not found (deleted meanwhile), or failed with Key Vault's status and error code, never its message. Key Vault replaces a version's tags as a whole on update, so adding or removing one tag reads the item's current tags with the call its own page uses (`GET /secrets/{name}/versions` for a secret, never a value read; `GET /keys/{name}` and `GET /certificates/{name}` for the others) and writes the full set back in one `PATCH`. A change made by someone else between that read and write can be lost; the window is one item's two calls. A tag that would take an item past 15 is refused for that item, not dropped. Expiry uses the edit form's date rules (end of the chosen day, UTC, in the future, before any start date) and can only be set or changed: Key Vault can't remove one. Code: `src/routes/bulk.rs`, with the four-at-a-time runner in `src/routes/batch.rs`, shared with import.
- **Secret types.** The create form offers Password (one value, as before) and four types with several fields: Login (`url`, `username`, `password`, `notes`), Database (`server`, `database`, `username`, `password`), API key (`key`, `endpoint`, `notes`) and SSH private key (`username`, `host`, `private_key`, `passphrase`). The value is compact JSON built by serde_json, every field present in the type's order, and the content type is `application/vnd.keyring.<type>+json;v=1`. Nothing is stored outside Key Vault and other tools see a plain JSON string. Every field is part of the secret value, including URL, username and server: each is read from the form straight into a `Secret`, never logged, never put in an audit event, address, flash message or error page, and never put back into a form that failed its checks. Showing any field is a reveal (`getSecret`, audited as `secret.reveal`), and the page says so. Lists and the secret's page show the type's name from the content type, without reading a value. Reading is strict and bounded (`src/secret_types.rs`): a value over 25 KB isn't parsed, at most eight entries are read, and a value that isn't an object of exactly the type's fields as strings, or a type or `v=` this build doesn't know, is shown as a plain value with a warning, never an error page. Field length caps apply, and Key Vault's 25 KB limit is checked on the encoded JSON with an error naming the field taking the most room. "Set a new value", "Edit details" and rollback keep the content type, and a Keyring content type can't be typed by hand onto a plain secret. For Database the reveal page also builds SQL Server (SqlClient) and PostgreSQL (libpq keyword/value) connection strings from the fields, quoting every part by that format's rules, and leaves them out when a field has a control character.
- The rotation line on a secret's page (`src/rotation.rs`) comes from its `rotation`, `rotation-last` and `rotation-status` tags. They are untrusted text: cleaned, cut to 64 characters, escaped, and shown as unknown when they don't follow the format. The expiry dashboard lists secrets tagged `rotation-status=failed` from the tags its list calls already return. Keyring doesn't rotate anything; see [rotation.md](rotation.md).

## Certificates

- The list and pages use the certificates API (7.5), which only returns the public certificate. Subject, issuer, validity, serial and other names are read from the DER with `x509-cert` 0.3 (RustCrypto, pure Rust). It brings its own `der` 0.8, `spki` 0.8 and `const-oid` 0.10, alongside the older versions other crates use, plus `tls_codec`.
- The list is read 25 at a time from Key Vault and shown 100 to a page.
- **Create.** The issuer is a select: Self, plus the vault's own issuers from `GET /certificates/issuers`. `Unknown` is refused on the server, since Keyring can't show the signing request or merge a signed certificate. If the issuer list can't be read (403 without Certificates Officer), only Self is offered, with a note saying why. A self-signed create comes back `inProgress` and shows as "Being created" until Key Vault finishes it, usually within seconds. `days_before_expiry` is checked against Key Vault's limit of 27 days per month of validity.
- **Renewal.** What happens near expiry can be changed from the certificate's page (`/v/{vault}/certificates/{name}/renewal`), with the same three choices as the create form: renew, email the vault's contacts, or nothing. It sends `PATCH /certificates/{name}/policy` with only `lifetime_actions`, so the rest of the policy is left as it is. Once a certificate has an action, "nothing" is refused before Key Vault is called: Key Vault answers 200 to an empty list (or `null`, or the field left out) but keeps the old action, as a real vault showed on 13-11-2026. Removing it needs the portal, or a new certificate. The days are checked against the same limit as create, using the validity from the current policy. A certificate whose issuer is `Unknown` (an import) can't be set to renew, on the page or on the server. A percentage trigger or more than one action is shown with a warning that saving replaces it. Key Vault's 400 shows as "Key Vault said:".
- **Pending requests.** A request waiting for its issuer can be stopped with "Cancel this request": a PATCH with `cancellation_requested: true`, then a DELETE of the operation, which frees the name.
- **Upload.** The file is read and shown as a preview before anything is sent: the leaf certificate's subject, issuer and dates, and if the name already exists, that the upload becomes a new version of it. A PEM must hold the certificate and an unencrypted PKCS #8 key (`BEGIN PRIVATE KEY`); PKCS #1 and SEC1 keys are refused with the openssl command that converts them, and the key must match the certificate. A BER-encoded PFX, which Keyring's own parser can't read, can still be uploaded, with a note that there's no preview. The file waits in the server-side session, never a cookie.
- **Enable and disable** set `attributes.enabled` on the current version.
- Expiry bands: expired, within 30 days, within 90 days.
- `.cer` (DER) and PEM downloads are the public certificate only, and need certificate read access.
- The private key lives in the certificate's backing secret. "Download with private key" is only offered when the policy marks the key exportable. It shows a warning and needs the name typed, then reads the backing secret (so it also needs secret read access) and sends it with `no-store`. The backing secret URL from Key Vault is only used if it is exactly `/secrets/{name}/{version}` on the same vault, with the certificate's name and a 32 hex character version. Each download logs at `warn` with subject, vault and name.

## Keys

- Keyring only ever reads keys with `GET /keys/{name}` and the list and versions calls, which return the public part. There is no export, backup, release, decrypt, unwrap or sign call anywhere; a test checks the keys client source for them.
- The JWK type only has public fields (`n`, `e`, `crv`, `x`, `y`). Any private field Key Vault might send is dropped while parsing.
- Public keys are shown as JWK and as PEM (SubjectPublicKeyInfo). The PEM is built with a few lines of DER encoding and tested byte for byte against openssl output for RSA and EC.
- Create defaults to RSA 3072 with every RSA operation, or sign and verify for EC. An HSM key on a Standard vault is refused by Key Vault (403, inner code `HardwareKeysNotSupported`), and the form says the vault needs the Premium tier.
- The list is read 25 at a time from Key Vault and shown 100 to a page.
- Rotate now and the rotation policy use Key Vault's own rotation API. The policy form rotates either a number of days after each version is made or a number of days before it expires, with an expiry and a near-expiry event. Durations Key Vault already holds (for example `P18M`) are sent back unchanged if the field wasn't changed. A policy with parts the form can't show, such as a time in hours, is listed on the page, and saving needs "Replace the whole policy" ticked. Key Vault's default policy (one Notify 30 days before expiry, no expiry) is shown as no policy set.
- **Enable and disable** set `attributes.enabled` on the current version.
- **Managed keys**, the ones Key Vault made for a certificate (`managed: true`), are refused on the server for delete, rotate, rotation policy and enable or disable, with a page that sends you to the certificate.

## Audit

The audit view reads Key Vault diagnostic logs (`AzureDiagnostics` or the `AZKVAuditLogs` resource-specific table) from the Log Analytics workspace linked to each vault, again as the signed-in user. If the user can't read the workspace, the page says so.

- The vault's diagnostic settings are read through ARM to find workspaces receiving `AuditEvent` (or the `audit` or `allLogs` category groups). "Dedicated" destinations use `AZKVAuditLogs`, others `AzureDiagnostics`.
- Queries go to the Log Analytics resource-centric endpoint (`/v1/<workspace ARM ID>/query`) with the user's OBO token for `https://api.loganalytics.io/.default`.
- **No query injection.** Filters are checked against strict patterns first (names: letters, digits and hyphens; people: letters, digits, `@ . _ -`; actions: a fixed list), so anything else is refused before a query is sent. Values then appear only as escaped string literals in `let` lines at the top of the query; the rest of the KQL is fixed text. Time ranges come from a fixed list.
- Operations are shown in plain words ("Viewed secret value" for `SecretGet`). Up to 500 most recent rows. CSV export uses the same query and rows, with formula guarding.
- **One outcome rule** (`Outcome::of` in `src/azure/audit.rs`), for this page, its CSV, the reports across vaults and "Used by". The query reads the HTTP status (`HttpStatusCode` in `AZKVAuditLogs`, `httpStatusCode_d` in `AzureDiagnostics`), `ResultSignature` and `ResultType`. The numeric status wins when there is one: 202 is **Accepted** (Key Vault took the request and finishes it shortly, as for every certificate create), any other 2xx is **Allowed**, 401 and 403 are **Refused**, any other 4xx or a 5xx (such as 404, 429 or 500) is **Failed**. Without a status, a known signature decides (`OK`, `Created`, `NoContent`, `Accepted`, `Forbidden`, `Unauthorized`), then `ResultType` `Success`. Anything else is **Unknown**, never Refused. So a row with `ResultType` `Success` and status 403 is Refused. The reports' KQL builds an `Outcome` column from the same lists (`outcome_kql`). The CSV has an Outcome column with the word and a Result column with what Azure wrote, such as `202 Accepted`.
- When a vault logs to several workspaces and some can't be read, the others are still shown, and the page and the CSV say how many were left out and why. If none can be read, the CSV answers 403 or 404 with an explanation instead of an empty file.
- Each secret, certificate and key page has "Who used it", which opens the audit view filtered to that item for the last 30 days.

### Keyring activity

Optional (`KEYRING_AUDIT_WORKSPACE_ID`, checked at start to be a Log Analytics workspace's ARM resource ID). `/v/{vault}/audit/keyring` shows Keyring's own audit events for the vault from `KeyringAudit_CL`, beside Key Vault's log, with a link between the two. Code: `src/azure/audit_keyring.rs` (query) and `src/routes/audit_keyring.rs` (page).

- Read as the signed-in person, with their Log Analytics OBO token, at the resource-centric endpoint (`/v1/<workspace ARM ID>/query`), like the vault's audit page. Never as Keyring's managed identity: it can only write rows through the data collection rule, and reading as it would show people rows they have no right to see. A 403 shows what to ask for (Log Analytics Reader on the workspace).
- **No query injection.** The vault, item and person are checked with the same patterns as the audit page, the action against Keyring's own action names, and each reaches the query only as an escaped string literal in a `let` line. The time range comes from the fixed list. Up to 500 rows, newest first. The columns it reads are all in `sink::COLUMNS` (tested).
- The reason and ticket columns (#205) are free text people typed, shown escaped like everything else, never as markup.
- Without the setting the route answers 404, the audit page has no link to it, and no query goes to the table.
- It only reads, so it writes no audit event.
- **Later.** Showing the reason and ticket next to Key Vault's row in an item's "Used by" needs the `kv_request_id` to `CorrelationId` join confirmed on a real vault first.

### Used by in the last 30 days

Each secret, certificate and key page, and the forms that change one (Set a new value, Roll back, Disable, Rotate and Delete), has a "Used by in the last 30 days" panel: the distinct callers in Key Vault's audit log, each with its kind (person, app or managed identity), sign-in name or app ID, object ID, last use, number of uses, and up to three client infos (user agents) and IP addresses. Code: `src/azure/used_by.rs` (query) and `src/routes/used_by.rs` (panel), shown by `templates/_used_by.html`.

- What counts: allowed `SecretGet` for a secret, and for a certificate the same on its backing secret (which holds the private key and has the certificate's name). For a key, `KeySign`, `KeyVerify`, `KeyWrap`, `KeyUnwrap`, `KeyEncrypt` and `KeyDecrypt`. Refused calls don't count.
- One fixed query per workspace the vault logs to, `summarize count(), max(TimeGenerated) by ObjectId, AppId, Upn`, over `AZKVAuditLogs` (claims from `Identity`, plus `ClientInfo` and `CallerIpAddress`) or `AzureDiagnostics` (`identity_claim_appid_g`, `identity_claim_oid_g`, `identity_claim_upn_s`, `clientInfo_s`, `CallerIPAddress`). A caller with a sign-in name is a person; one whose token carries a managed identity resource ID (`xms_mirid`) is a managed identity; any other with an app ID is an app. Workspaces' answers are merged by caller, latest first, up to 100.
- **No query injection.** The vault and item names are already-checked names (letters, digits and hyphens), checked again, and reach the query only as escaped string literals in `let vaultName` and `let itemName` lines. The operations and the 30 days are fixed text.
- As the signed-in person, with their ARM and Log Analytics tokens, like the audit view. Nothing uses Keyring's managed identity.
- **Advice, not a gate.** The panel runs beside the page's own reads (`tokio::join!`) with a 5 second limit of its own, so it never holds up a form for longer than that. If the vault has no diagnostic setting to a workspace, the person can't read the settings or the workspace, consent is missing, or Azure is slow or fails, the panel says why in plain words, with what to ask for, and the form works as before. Some workspaces failing still shows the rest, with a note.
- **An empty list is not proof.** Logs arrive late, a new diagnostic setting has no history, retention ends, and a workspace that can't be read hides its callers, so the panel never says a change is safe. Each query also returns one row counting all the vault's events in the period (`VaultEvents`), so the panel can tell these apart: callers found (listed); every workspace answered with the vault's events but none for this item ("No secret reads found in the available logs for this period. Logs may be delayed or incomplete; check consumers before changing this secret.", with key use or certificate private-key access in place of secret reads); no events from the vault at all, or the table missing (Log Analytics answers 400 with a semantic error such as `SEM0100` until the first event arrives; the exact code is on the real-vault checklist), which is unknown history, shown like a log that can't be read; a workspace the person can't read; and some workspaces failing or a `PartialError` answer, where an empty list says some of the log is missing. Under the panel in every state: how many of the vault's workspaces answered, the 30 days, the newest event from the vault, and what the log can't show. `tests/used_by.rs` fails if any template or `src/routes/used_by.rs` promises a change is safe.
- The panel only reads, so it writes none of Keyring's own audit events.

### Across vaults

`/audit` with no vault runs fixed reports over every vault the person can see (the first 100 by name, chosen by `src/routes/every_vault.rs` as for search and the expiry dashboard). Code: `src/azure/audit_across.rs` (queries) and `src/routes/audit_across.rs` (page and CSV).

- Each vault's diagnostic settings are read through the shared fan-out (`src/azure/fanout.rs`), six at a time. Vaults are then grouped by workspace and table, so vaults sharing a workspace are covered by one query. The queries run a few at a time too. The two stages share the fan-out's minute, half each, and each vault or workspace keeps its 20 second limit, so the page keeps to the same minute as the expiry dashboard and search.
- Five reports, each a fixed link and a fixed query: secret values read (allowed or accepted `SecretGet`), private keys downloaded, deletes, purges and recoveries, refused requests (401 or 403) counted by person and vault, and activity by one person. "Private keys downloaded" counts an allowed `SecretGet` whose name matches a certificate the same vault's logs mention in the same range, since a certificate's private key is read through its backing secret of the same name. Keyring's own `.pfx` download always reads the certificate first, so it is always counted. Another tool that reads only the backing secret, in a range with no certificate call, is counted under secret values read only.
- **No query injection.** The vaults' ARM resource IDs reach the query only as escaped string literals in `let vault0 = "...";` lines, matched with `_ResourceId in~ (vault0, vault1, ...)`. IDs are checked with the same pattern as every other ARM ID first, so an odd one is never sent. The person filter is checked as on the vault's own page and goes in a `let who` line. Everything else is fixed text, and the time range comes from the fixed list.
- All of it as the signed-in person: ARM with their ARM token, Log Analytics with their Log Analytics token. Nothing uses Keyring's managed identity.
- Up to 500 rows, newest first, across all workspaces (the refused report sums counts by person and vault first). The page and the CSV both list vaults with no diagnostic setting, vaults whose settings couldn't be read, workspaces that couldn't be read (with the vaults they cover and the reason) and any cap, so neither can pass for a full report. CSV fields are formula-guarded as elsewhere.
- Each row links to the vault's own audit page, filtered to the item (or, for refusals, the person) and the same range.
- The old addresses from before the vault was in the path (`/audit?item=...`, `/audit.csv` with no report) still go to the vault last used.
- The page only reads, so it writes no audit event.

## Access

`/v/{vault}/access` shows who can reach a vault's contents, and each secret, certificate and key page has an Access section for that item. Code: `src/azure/authz.rs` (the ARM calls) and `src/routes/access.rs` (page, section and CSV).

- **RBAC vaults.** `GET {scope}/providers/Microsoft.Authorization/roleAssignments?api-version=2022-04-01`, where the scope is the vault's ARM ID, or `{vault ID}/secrets/{name}` (and `/certificates/{name}`, `/keys/{name}`) for an item. ARM returns assignments at, above and below the scope. Keyring keeps the ones at or above it, and says where each comes from: this item, the vault, the resource group, the subscription, a management group or the whole tenant.
- **Eligible assignments.** `roleEligibilityScheduleInstances` with `$filter=atScope()` at the same scope (api-version 2020-10-01), shown with an "Eligible" badge. If that call fails (a tenant without PIM, or no permission), the active ones still show, with a note.
- **Roles.** Each role used is read once from `roleDefinitions/{id}` at the vault's scope, six at a time, up to 50 roles a page. Only roles with a `Microsoft.KeyVault/` data action (or `*`) are listed, plus Owner, Contributor and User Access Administrator, which are flagged "Can grant itself access": they don't reach the contents, but can add a role or policy that does. Reader and other control-plane roles are left out. A role that can't be read is listed as "Role not read", never dropped.
- **Access policy vaults.** `GET {vault ID}?api-version=2023-07-01` gives `enableRbacAuthorization` and `properties.accessPolicies`. Each policy is shown by object ID with its permissions in plain words ("read values, list"), and a "Reads secret values" badge where it allows secret `get`. On an item's page only the policies for that kind of item show, since policies apply to the whole vault. Data roles don't apply on these vaults, so only the roles that can grant access are listed.
- **Principals** are shown by object ID and type (User, Group, App or managed identity), with a link to the object in the Azure portal. Keyring doesn't call Microsoft Graph, so it has no names for them, and group members aren't expanded: the page says "Group" and links to it. Adding names would need a Graph permission and a new consent, and is left for later.
- **When it can't be read.** A 403 on role assignments or the vault resource gives a plain explanation and the role to ask for (Reader on the vault, its resource group or subscription), never an empty table. The CSV answers 403 with the same explanation instead of an empty file.
- **Time limits.** The vault page gives the reads 20 seconds. An item's page runs them beside its own Key Vault reads with a 5 second limit, so a slow or failing ARM read never slows or breaks the item page: the section shows the reason instead.
- **CSV.** `/v/{vault}/access.csv` has one line per assignment or policy (object ID, type, role or permissions, active, eligible or access policy, where it comes from, scope, can grant itself access, condition), with formula guarding, and `NOT READ` lines for anything left out.
- All calls use the person's on-behalf-of Management token. Nothing uses Keyring's managed identity, and no new token resource or permission is needed. The page only reads, so it writes no audit event.

## Permission hints

Buttons the person's roles don't allow are disabled, with the role they need as visible text beside them ("Needs Key Vault Secrets Officer"), the same role the 403 page names. They are never hidden. Code: `src/routes/hints.rs`, with the ARM call in `src/azure/authz.rs` (`permissions`).

- **The read.** `GET {scope}/providers/Microsoft.Authorization/permissions?api-version=2022-04-01` with the person's on-behalf-of Management token. It gives `actions`, `notActions`, `dataActions` and `notDataActions` for each of their roles at that scope. The vault's access model comes from `GET {vault ID}` at the same time.
- **Matching.** Each Keyring action maps to the Key Vault data actions it needs, listed in the code beside the action (`Action::data_actions`). Patterns match without regard to case, and `*` matches any run of characters. A role allows an action when one of its `dataActions` matches and none of its `notDataActions` does; any one role allowing it is enough, since `notDataActions` aren't a deny.
- **Scope.** Lists ask at the vault's scope. Item pages (and a deleted item's page) ask at the item's own scope (`{vault ID}/secrets/{name}` and so on), never only at the vault's, so a role given on one item isn't missed. "Download with private key" is never hinted, because it reads the backing secret, whose own scope isn't asked.
- **Kept.** Each scope's answer is kept in the session's memory for five minutes and dropped by the session sweep or with the session. Nothing is written anywhere.
- **Bulk changes.** The "Review changes" button under "With selected" on each list uses the vault-scope hint for updating that kind (`secrets/update/action`, `certificates/update/action`, `keys/update/action`). A role given on single items doesn't show at the vault's scope, so the button can be disabled for someone who could change a few of the items; Key Vault still decides each one.
- **Fails open.** If the read fails, is refused, can't be read, or takes more than 2 seconds (it runs beside the page's own reads), or the vault uses access policies (which `permissions` doesn't cover), every button stays enabled.
- **Only a hint.** Key Vault decides. No handler reads hints, every POST route is unchanged, and a person whose button was disabled can still post the form and gets Key Vault's own answer. Only reads, so it writes no audit event.
- **PIM.** A 403 page offers to turn on an eligible role. See [PIM activation](#pim-activation).

## PIM activation

Where a person is eligible for a Key Vault role through Privileged Identity Management (PIM) for Azure resources, Keyring offers to turn it on for them, as them. Keyring keeps no request state: what is on, eligible or waiting for approval is read back from ARM every time. Code: `src/azure/pim.rs` (the ARM calls) and `src/routes/pim.rs` (offer, form, My access).

- **Calls.** All through ARM with the person's on-behalf-of Management token, api-version 2020-10-01, so no new permission or consent: `roleEligibilityScheduleInstances` and `roleAssignmentScheduleInstances` with `$filter=asTarget()` at the vault's ID (each lists the person's own, including through groups, and Keyring keeps the ones at or above the vault), `roleAssignmentScheduleRequests` with `$filter=asRequestor()` for requests still waiting, `roleManagementPolicyAssignments` at the eligibility's scope for the role's PIM settings, and `PUT roleAssignmentScheduleRequests/{new GUID}` at the eligibility's own scope with `requestType` `SelfActivate` (with `linkedRoleEligibilityScheduleId`, `scheduleInfo` `AfterDuration`, `justification` and `ticketInfo`) or `SelfDeactivate`. No Graph, no managed identity, no app-only call.
- **The offer.** Only when a 403 is a Key Vault RBAC refusal (`ForbiddenByRbac`) on a vault page that names a role (`Problem::pim_need`), a layer looks up the person's eligibility for that one role (by its built-in GUID) at or above the vault. It runs in its own task, so its calls don't change the request's audit event, with a 5 second limit. If it finds one, the same page gains "Activate {role}" under "What to ask for"; on any failure, 403, 404, timeout, a tenant without PIM, or no matching eligibility, the page is byte for byte what it was. A firewall refusal, a plain `Forbidden`, the vault list and the audit pages never look. Keyring turns on and off only the built-in Key Vault roles its 403 pages name. Any other role, such as Owner or Contributor, is refused before any call, whatever the address or form says, and My access marks it "Activate in PIM".
- **The form.** `/v/{vault}/my-access/activate?role={GUID}&back={path}` reads the eligibility and the role's PIM settings again (`effectiveRules` with `caller` `EndUser` and `level` `Assignment`): the maximum from `Expiration_EndUser_Assignment`, and whether `Enablement_EndUser_Assignment` asks for `Justification`, `Ticketing` or `MultiFactorAuthentication`, and the approvers from `Approval_EndUser_Assignment`. If the settings can't be read, it offers up to 8 hours (PIM's default) and asks for a reason. Duration is checked against that maximum on the server, never above 24 hours whatever the policy says. Justification (5 to 200 characters), ticket system and number (64 each) have control and invisible characters taken out and white space folded before they go to ARM or the log. With `KEYRING_STEP_UP_*` set the form asks for step-up first, like a reveal. Where the person is eligible at more than one scope, the role is turned on at the one nearest the vault (the vault, then its resource group, then its subscription), so it applies to as little as possible. Nearness is by kind of scope, never by the length of its ID. Keyring can't cheaply check that a management group contains the vault's subscription, so a management group or the tenant root is used only when nothing nearer is on offer; ARM returned it for a query at the vault and refuses the request if it doesn't apply. A scope, role definition ID or schedule ID from ARM that isn't a plain ARM path is dropped before it is offered or put in a request. The form and every link to it carry the scope and schedule ID of the eligibility they show. They are only a key: on the post Keyring reads the eligibilities again and uses that same one, taking the scope it sends to from ARM's answer. If it has gone or changed, nothing is sent and the form is shown again with what is on offer now and a note that it changed. It never falls back to another scope on its own.
- **Results.** `Provisioned`, `Granted` and the other done states: "Role turned on", with Try again back to the page that was refused (Key Vault can take a few minutes to see it). `PendingApproval` and its kin: "Waiting for approval", naming approvers only as PIM's own settings describe them (no Graph), and a link to PIM in the portal. Anything else: refused, with ARM's status or error code, never its message. A `RoleAssignmentRequestPolicyValidationFailed` that names `ExpirationRule`, `JustificationRule`, `TicketingRule` or `MfaRule` puts the person back on the form with a plain sentence; only those names are read from the message. Every refusal or failure of an activation or deactivation is recorded on its audit event as `denied` (401 or 403) or `failed`, with ARM's error code, including when the page shown is a redirect with a message.
- **Stronger sign-in.** When PIM refuses with `RoleAssignmentRequestAcrsValidationFailed` and a claims challenge (seen as `&claims=` and URL-encoded JSON in the message; base64 is accepted too), Keyring checks it (a JSON object of at most 4 KB, only `access_token` or `id_token`, only `acrs` with context IDs `c1` to `c99`), rebuilds it from the parsed value, keeps it in the session where `/auth/start` picks up claims challenges (#235), and offers "Confirm it's you" back to the empty form. The justification is never in a URL. A challenge in any other shape is not passed on.
- **My access.** `/v/{vault}/my-access`, in the vault's navigation, lists the person's own Key Vault roles at or above the vault: on now (with time left, and Deactivate for ones turned on through PIM, `assignmentType` `Activated`), starting later, eligible (with Activate, or "On now", "Waiting for approval" or when it becomes eligible), and requests waiting for approval. ARM lists current and upcoming instances, so an assignment or eligibility counts as on now only when `startDateTime <= now < endDateTime` (no start is already started, no end is no end); one that starts later is shown under "Starting later" with no Deactivate, an eligibility that starts later offers no Activate (on the 403 page or the form either), and one with a time Keyring can't read isn't shown, with a note. Waiting requests are listed from `asRequestor()` itself, so they still show when the eligible list can't be read. Each list that can't be read, the requests included, gets its own note. Deactivate reads the active list again and only sends a `SelfDeactivate` for a role ARM lists as activated for this person at that scope. The built-in Key Vault roles are recognised by their GUIDs, so they are listed and can be turned off even when their role definition can't be read; for any other role whose definition can't be read, the page says the list may be incomplete.
- **Audit.** `role.activate` and `role.deactivate`, through `audited(...)`, with the form token and origin check. The event has the role GUID in `role`, the scope in `role_scope`, the duration in `role_duration`, the justification in `reason` and the ticket in `ticket`. Waiting for approval is `success` with `reason_code` `PendingApproval`.
- After a role is turned on or off, the permission hints kept in the session are dropped, so buttons are read again.

## Expiry dashboard

The dashboard reads secrets, certificates and keys from every vault the person can see, six vaults at a time. Each vault has 20 seconds and the whole page 60, so one slow or private vault can't hold up the rest. Vaults that couldn't be read, or ran out of time, are listed with the reason, on the page and in the CSV. The fan-out (how many at once, the limits and the reasons) lives in `src/azure/fanout.rs`, and the reading of each vault's lists in `src/routes/every_vault.rs`, shared with search.

## Age view

`/expiry/age` groups every secret, certificate and key across vaults by how long since its value last changed: under 90 days, 90 to 180, 180 to 365, and over a year (more than 365 days). It reads through `src/routes/every_vault.rs`, like the expiry dashboard and search, so it has the same limits, lists the vaults it couldn't read (on the page and in the CSV), and shares the session's one-minute list cache. It only reads, as the signed-in person, and makes no list call of its own and no value read.

- **The date.** Key Vault makes a new version for every new value, so the current version's `attributes.created` is when the value last changed. Editing properties (tags, dates, enabled) moves `updated`, not `created`, so `updated` isn't used. The view assumes the list calls (`GET /secrets`, `/certificates` and `/keys`) give the **current** version's `created`, not the first version's. The mock Key Vault does; a real vault is still to be confirmed (see the [checklist](real-vault-checklist.md), "Age: list gives the current version's created"). If a real vault gives the first version's date, the age view would need a versions call per secret, which is far more expensive, and should then be limited to one vault at a time.
- **What's left out.** A secret or key that backs a certificate changes with the certificate, so it is left out and the certificate is shown by its own current version. On each vault's lists it never gets the badge.
- **The badge.** `KEYRING_STALE_AFTER_DAYS` (default 365, from 1 to 3650, checked at start) sets when "Not changed in over a year" (or "over N days") shows: on the age view, on the secrets, certificates and keys lists, and on each item's page. The four bands stay fixed whatever it is set to.
- **Per vault.** The secrets list's "Value changed" column replaces "Updated", and the filter "Not changed in over N days" (`?older=N`, 1 to 36500) leaves out certificate-backed secrets. A number it can't use filters nothing and the page says so.
- **CSV.** `/expiry/age.csv` has the vault, type, name, enabled, the date the value changed, days since, the band and tags, with the same formula guarding as the expiry CSV, and a `NOT READ` row for each vault not read.

## Well-known tags

Key Vault has no description or owner field, so Keyring reads and writes a few tags by name. They are ordinary tags: they show in the portal and the CLI, anyone who can read the item's properties can read them, each counts towards Key Vault's 15 tags per item, and Keyring stores nothing of its own.

| Tag | On | What Keyring does with it |
| --- | --- | --- |
| `description` | secret, certificate, key | The item's note (#254). Set from the Description field, shown under the heading and in a list column, matched by search and list filters |
| `rotation`, `rotation-last`, `rotation-status` | secret | Read only, for the rotation line ([rotation.md](rotation.md)) |

`owner`, `notify` and the vault tag `keyring-owners` (#255) are planned for this table.

**The description.** Code: `src/description.rs`, one place for the rules, used by every form, the import, the bulk change and Edit details.

- **Length.** At most 256, counted in UTF-16 code units. Key Vault's limit on a tag value is 256 characters, and Key Vault is a .NET service, where a string's length is its UTF-16 code units. A browser's `maxlength` and a script's `value.length` count the same units, so the field, the counter and the server agree. A letter such as `é` or `日` counts once; a character outside the Basic Multilingual Plane, such as most emoji, counts twice. That Key Vault counts this way is on [real-vault-checklist.md](real-vault-checklist.md).
- **Characters.** The same checks as a reveal reason (`crate::reason`): no control characters and no invisible format characters (bidi marks and overrides, zero-width characters, tag characters, private use and the rest that list names). Line breaks are allowed, stored as `\n` (CRLF and a lone CR both become LF), and kept on the detail page. Ends are trimmed.
- **Writing it.** The note is merged into the item's tags, never written over them. Every path reads the current tags, sets or removes `description`, and sends the whole set, because Key Vault replaces a version's tags as a whole. An empty field removes the tag. Adding a note to an item that already has 15 tags is refused with a field error before Key Vault is called. Changing an existing note doesn't add a tag.
- **Where.** A Description field on secret create, Edit details and Set a new value, certificate create and upload, and key create; **Edit details** for certificates and keys (below). The import reads an optional `description` CSV column, the bulk change can set or remove it, and copy to another vault brings it with the tags. The tag rows never show `description`, and `description` typed in a row as an ordinary tag name is refused with a message pointing at the field (the import says to use its column; the bulk tag change says to use its description changes). The name is matched exactly, as Key Vault keeps tag names: `Description` is an ordinary tag.
- **Shown.** Under the item's heading, in a Description column on the secrets, certificates and keys lists, search results and the import preview (cut to 80 characters on one line, with the whole note as the cell's visually hidden text), and in its own column in the expiry and age CSV exports, through the same formula guard as every other text field.
- **Never logged.** The note can hold sensitive context, so it is never logged and never put in an audit event: editing it is a `*.update` event like any property change, with the vault, item and version only. The form structs print without it. `tests/no_secrets_in_logs.rs` captures every line at TRACE through create, edit, a refused edit and both Edit details paths, including a Key Vault refusal, and checks the note text appears nowhere. The form says not to put secrets or personal details in it.

**Edit details for certificates and keys.** `GET` and `POST /v/{vault}/certificates/{name}/details` and `/v/{vault}/keys/{name}/details` (`src/routes/details.rs`). The form holds the description and the tag rows, and posts the version and its `updated` time. The post goes through `audited(...)` (`certificate.update`, `key.update`), so it has the same form token check, origin check, reason gate and audit event as the other changes; the Edit details button carries the same permission hint (`certificates/update/action`, `keys/update/action`); it isn't a step-up action, like enable and disable. Then, as the person: read the current version (`GET /certificates/{name}` or `GET /keys/{name}`), refuse if the version or `updated` time differs from the form's (someone changed it since), merge, and send `PATCH /certificates/{name}/{version}` or `PATCH /keys/{name}/{version}` with `tags` and an empty `attributes`, so the enabled flag, dates and the certificate policy are left as they are and no new version is made. Nothing is sent when nothing changed. A certificate's key is refused, as for its other changes. Tags a row can't show (below) are listed and kept.

**Tag rows** (#253). Code: `src/routes/tag_rows.rs`, used by secret create, Edit details and Set a new value, certificate create and upload, key create, and Edit details for certificates and keys. Each tag is a row: a name input and a value input.

- **Fields.** Row `n` posts `tag-name-n` and `tag-value-n`, `n` from 1 to 40, and the form posts `tag-rows=1`. The field names are also the inputs' ids, so an error is shown beside its row and the summary links to it. Indexed names pair a name with its value whatever is typed or left out, in any order. More than 40 rows, a number written another way (`0`, `01`, `+1`) or a field sent twice refuses the form, never guessed at. A row with no name and no value is skipped, so clearing a row (or removing it with the script) removes that tag. A value without a name is an error on that row. A post with no tag fields at all (no `tag-rows`) leaves the tags as they are; a post with the old `tags` box, from a page opened before this change, is refused with "This form changed since you opened it".
- **Checks.** The same as before, now per row: a name is required, `description` is refused with a pointer to the Description field, names up to 512 and values up to 256 characters, a name used twice (exact, as Key Vault keeps case) is refused on the later row, and 15 tags with the note counted. Names and values are kept exactly as typed, spaces and `=` included.
- **What a row can't show.** A text input drops line breaks, and HTML can't carry a NUL, so a tag with `\r`, `\n` or `\0` in its name or value, or with a blank name, is listed under the rows and kept as it is on every write. A row can't take such a tag's name. Every other tag round-trips: read, shown in a row, posted back, merged, and nothing is sent when nothing changed.
- **Suggestions.** Plain `<datalist>`s, so they work without JavaScript: `tag-names` (names used in this vault, most used first), `tag-values-any` (the most used values overall, for a new row) and one list per name (`tag-values-n`, the values used with that name, for an existing row). Read from the vault's list calls as the person (`GET /secrets`, `/certificates` and `/keys`, names and properties only), through the per-session list cache (see [Search](#search)), so a form opened within a minute of a list page or another form makes no new call. Never a value, never the `description` note. Capped at 200 names and 50 values per name; a name or value over 100 characters, or holding a hidden character (as `crate::reason` defines them), isn't suggested. The read has 2 seconds; past that, or if the lists can't be read, the form shows without suggestions and works the same. On the form pages that read the item (secret edit and set value, certificate and key Edit details, certificate create's issuer list), it runs beside that read, not after it. What each form now reads: secret create, key create and certificate upload add the vault's three list calls (or none, from the cache), bounded by the 2 seconds; the others add the same in parallel with what they already read. A form shown again after an error reads them again, through the cache. The certificate upload's "file too big before the form token arrived" path reads nothing.
- **Script.** `static/tags.js` (a third same-origin script, under 150 lines by a test) swaps a row's value list when its name changes, and adds and removes rows. It builds rows with `createElement` and `textContent` only, compares names as text (never in a selector), and stops at the 40 the server reads. Without it the rows and the suggestions work the same, with three empty rows to add tags.
- **Filter boxes.** The tag filter on the secrets, certificates and keys lists, the vault list, the expiry dashboard and the age view, and the search box, have a `<datalist>` of `name` and `name=value` from the items that page already read (the vault list from the vaults' own tags), up to 200. Certificates and keys gained the same `tag` filter as secrets.
- **Tag links.** Each tag on a secret, certificate or key page links to its list filtered by `name=value`, the query value percent-encoded. A tag the filter couldn't find again (an `=` in its name, spaces at either end) is shown without a link.
- **Bulk change.** Keeps its one tag name and value per change, and gets the same suggestions from the list the page already read.
- **Unchanged.** The import (#217) still reads `tags` as `k=v;k=v` in its CSV, and copy to another vault (#215) still brings the tags as they are.

## Search

`/search?q=...`, and the box in the top bar, find secrets, certificates and keys across every vault the person can see. It reads the same lists as the expiry dashboard, with the same limits and the same notes for vaults it couldn't read, and never a value: only the list calls are made (`GET /secrets`, `/certificates` and `/keys`), never `GET /secrets/{name}` or a version.

- The text matches a name, a tag as `name=value`, the description, or a secret's content type, as a case-insensitive substring: the same match as each vault's own list filter. Certificates and keys have no content type in their list calls. Filters narrow by type, vault and status (expires within 30 days, expired, disabled).
- The text is capped at 100 characters, and the page at 500 results. It is a query string, so like every query string it is never logged. Search only reads, so it writes no audit event.
- Results are grouped by vault, with the same status badges as each vault's list, and link to the item's page under `/v/{vault}/...`.
- It is a plain GET form and works without JavaScript. There is no script for it.
- **List cache.** Reading every vault on each search would be slow and draw throttling. Each vault read in full is kept in the session for 60 seconds, in memory, and reused by the next search, the expiry dashboard and the age view. It holds names and properties only (the `Item` type has no field for a value). A vault that was only partly read is not kept. A form posted to a vault's pages drops that vault's list, before and after the change, so a change shows straight away. A copy to another vault drops the target vault's list the same way. Lists older than a minute are dropped by the session sweep, and every list goes with its session. Nothing is shared between sessions.

## Pinned and recently opened

A **Pin** button under the heading of each vault list (secrets, certificates, keys) and each secret, certificate and key page pins it, and opening an item adds it to **Recently opened** (the last 10). The home page and the vault list show both lists above everything else, when they have anything in them.

- **Kept in the browser.** `static/pins.js`, a second same-origin script, keeps the lists in `localStorage` under one key, `keyring.pins`. Each entry is a kind (vault, secret, certificate or key), a vault name, an item name and a local path. Never a value, version, tag or token. The server neither reads nor writes it, so "store nothing" still holds: Keyring has no copy, and another browser or person sees nothing. Pinned is capped at 50.
- **Checked before use.** Each stored entry is checked when read: the names must match Key Vault's naming rules, and the path must be exactly the `/v/{vault}/{secrets|certificates|keys}[/{name}]` path built from them. No scheme, no `//`, no backslash, no control characters. Anything else is dropped, never shown. Names are set as text, never markup, and the script has no `innerHTML` (tested).
- **Cleared on sign-out.** Submitting **Sign out** clears the list, and the signed-out page clears it again in case the first didn't run. A **Clear** button sits under the lists, with a line saying they are kept in this browser only and cleared on sign-out. Both use script event listeners, so the CSP is unchanged.
- **Optional.** Without JavaScript, when `pins.js` fails to load, or when the browser refuses or fills `localStorage` (private modes, quota), the Pin button never appears and the pages are as they were. Every storage call is wrapped, and the whole script stops quietly on any error.
- `pins.js` is kept under 200 lines and `app.js` under 450, both by tests.

## Vault health

`/vault-health` checks how each vault the person can see is set up. One row per vault, and each check is Pass, Warn or Unknown. Unknown always has a reason and is never counted as a pass: a value Azure didn't send, a setting Keyring doesn't recognise, or a read that failed or ran out of time.

| Check | Pass when | Read from | Role |
| --- | --- | --- | --- |
| Audit logs | A diagnostic setting sends `AuditEvent` (or the `audit` or `allLogs` group) to a workspace, storage account, event hub or partner | Diagnostic settings, ARM | Reader |
| Azure RBAC | `enableRbacAuthorization` is true | Resource Graph | Reader |
| Soft delete | `enableSoftDelete` is true. Missing is Unknown | Resource Graph | Reader |
| Purge protection | `enablePurgeProtection` is true. Azure leaves it out until it's on, so missing is a warning | Resource Graph | Reader |
| Network access | `publicNetworkAccess` is `Disabled`, or `networkAcls.defaultAction` is `Deny`. Missing values take Azure's defaults (`Enabled`, `Allow`) and warn. Any other value is Unknown | Resource Graph | Reader |
| Private endpoint | At least one private endpoint connection is `Approved` | Resource Graph | Reader |
| Secret expiry | Every enabled secret, other than a certificate's backing secret, has an expiry date | Secrets list | Key Vault Reader |
| Certificate renewal | Every enabled certificate's policy has an `AutoRenew` action | One policy read per certificate | Key Vault Reader |
| Key rotation | Every enabled key, other than a certificate's own, has a rotation policy with a Rotate action | One rotation policy read per key | Key Vault Reader |

- Vaults are read through `src/azure/fanout.rs`, as on the expiry dashboard: six at a time, 20 seconds each, a minute in all, and the first 100 by name across all vaults. A vault not read in time shows Unknown for the checks that need a read, with the reason; the Resource Graph checks still show.
- Certificate renewal and key rotation need a call per item, so they only run when one vault is picked. Across all vaults they're shown as "Pick this vault". In one vault, up to 200 certificates and 200 keys are checked, six at a time within 15 seconds. Items past that or not read in time make the check Unknown if nothing else failed it, and are named in the warning if something did.
- Each warning and unknown is listed under the table with one sentence on why it matters and what to do, and a link to Microsoft's guide for the setting.
- The CSV export has one line per vault and check (vault, subscription, resource group, check, result, detail, guide), with formula guarding, and `NOT READ` lines for a vault not in the list or vaults past the first 100.
- Only properties are read: no secret value, no private key. The page changes nothing, so it writes no audit event.

## Alerts

Expiry alerts are optional. Since Keyring stores nothing and has no identity of its own, alerts are delivered by Azure-native means (Event Grid `SecretNearExpiry` and `CertificateNearExpiry` events), set up through the deploy templates. The app itself never runs background jobs with stored credentials.

Sentinel content for Keyring's own audit table is optional as well (`infra/sentinel`, [sentinel.md](sentinel.md)). Its rules are Sentinel Scheduled rules, run by Sentinel, created turned off. Two of them compare Keyring's table with Key Vault's log, which needs Keyring's outbound addresses: Keyring can't know them, so they are a parameter, and without it those rules aren't created.

Access alerts are optional too. `infra/alerts/access.bicep` adds Azure Monitor log search alert rules on the vault's Log Analytics workspace: a read of a watched secret, any purge, or more than N refusals from one caller in 15 minutes. Each rule runs its query as its own system-assigned identity with Log Analytics Reader on the workspace. That identity belongs to Azure Monitor, has no role on any vault, and is never used by Keyring. The rules read the same columns and operation names as the audit view (`tests/alert_queries.rs` checks).

## Deploy

- The Docker image described above.
- `infra/app-service` and `infra/container-apps`: Bicep that runs the image, with Keyring's own config vault and a user-assigned managed identity. That identity can only read Keyring's two config secrets (client secret and session secret) through Key Vault references, and, with `auditWorkspaceId`, send rows through the one audit data collection rule (Monitoring Metrics Publisher, from `infra/modules/audit-sink.bicep`), and, with `notifyDomain`, send email from the one Communication Services resource in Keyring's own resource group (a custom role with only `CommunicationServices/Read` and `Write`, from `infra/modules/notify.bicep`). It has no role on any other vault or on any workspace's data, so it can't be used to reach user data. With `useFederatedCredential`, the app registration also trusts this identity as a federated credential, so there is no client secret to read.
- Optional VNet integration, private endpoints and private DNS so Keyring can reach private vaults (`docs/private-vaults.md`).
- `infra/alerts`: optional per-vault Event Grid subscription for near-expiry events, and optional log search alerts for reads of watched secrets, purges and repeated refusals (`docs/alerts.md`).
- `infra/sentinel`: optional Microsoft Sentinel content for `KeyringAudit_CL`: the ASIM Audit Event parser `vimAuditEventKeyring`, analytic rules (each created turned off, and each turned on by its own parameter), hunting queries and a workbook (`docs/sentinel.md`). Sentinel runs the rules as itself. `tests/sentinel.rs` checks every column they read against `sink::COLUMNS`, and every action, outcome and reason code against the ones Keyring writes.
- CI runs `az bicep build` on every template and example parameter file, and on each example copied next to its template the way the docs say. Nothing is deployed from this repository.

## Threat model

What Keyring protects, who it protects it from, and how. This is a summary for reviewers, not a guarantee.

### What's worth protecting

- **Secret values, private keys and certificates** in people's vaults.
- **People's Entra tokens**: their access token for Keyring's API, refresh tokens, and the Key Vault, ARM and Log Analytics tokens exchanged from them.
- **Keyring's own secrets**: the Entra client secret and the session secret.
- **The managed identity**, when Keyring uses it in place of a client secret or for the audit sink. Whoever controls it can act as the Keyring app registration (when it is the credential), add rows to `KeyringAudit_CL`, and, with email on, send email from Keyring's ACS resource.

### Trust boundaries

- **The browser** is trusted only with a random session ID in an http-only cookie. It never sees tokens.
- **Keyring's server** holds tokens in memory for each session and passes secret values through memory on the way to the browser. It has **no access of its own** to any vault.
- **Azure** (Entra ID, Key Vault, ARM, Log Analytics) makes every authorisation decision, as the signed-in person.
- **The managed identity** (when used as the credential) can act as the Keyring app registration. That gives it no vault access today: the registration has only delegated permissions, and the on-behalf-of exchange needs a signed-in person's token. This holds only while the app registration has **no application permissions**. If one is ever added, the identity could use it with nobody signed in, so keep the registration delegated-only and treat a new application permission as a security change.

### Threats and what stops them

| Threat | Mitigation |
| --- | --- |
| Keyring used to reach vaults a person can't | Every Azure call that reads or changes a person's data carries the person's own OBO token. Keyring has no managed identity, service principal or app-only token with vault access. Its managed identity can only read its own two config secrets and write audit rows |
| Stolen managed identity token used against the audit table | It could add made-up rows to `KeyringAudit_CL` through the one rule, but couldn't read, change or delete any row: Monitoring Metrics Publisher on that rule is its only role there. The writer columns on a row are whatever the sender put there, so with that token made-up rows can carry any writer or actor: treat the table as written by whoever holds the identity, and check a row that matters against Key Vault's own log by `kv_request_id`. No person has a role on the rule, so nobody can write rows with their own token |
| Stolen managed identity token used to send email | With email on, Keyring's identity can send email from its one ACS resource, and can change that one resource's settings (for example its linked domains), because Azure offers no narrower permission than Read and Write on Communication Services. It can't read or regenerate the resource's keys, and has no other Communication Services or Email Service access. The resource sits in Keyring's own resource group, so no other workload depends on it. A stolen token could send mail from Keyring's domain to anyone, outside Keyring's own allow-list and rate limit. What limits misuse: Keyring's recipient allow-list and rate limit (for mail sent through Keyring), ACS's own sending limits, ACS's logs, and the Azure Activity Log, which records any change to the resource's settings |
| Email used to leak values or to mail-bomb | Emails are built from fixed text, the type, checked item names and cleaned free text, never a value, token, private key, Azure message or reason (tested at TRACE over logs and every body sent). Recipients are strictly parsed `to` addresses only, held to the allow-list and to a rate limit per recipient per type. Addresses are never logged |
| Stolen session cookie | Random 256-bit ID, http-only, `SameSite=Lax`, `Secure` and `__Host-` prefixed over HTTPS. One hour idle and 12 hour absolute timeouts. Sign-out removes the session server-side. Optionally, step-up (`KEYRING_STEP_UP_*`) asks for a Conditional Access authentication context or a recent sign-in before a reveal, private key download, rollback or purge. It only challenges a session whose stored sign-in doesn't meet the settings: a stolen cookie from a session that already met them passes until that session ends or, with a maximum age set, until the sign-in is older than it. So set `KEYRING_STEP_UP_MAX_AGE` as well as a context if the cookie is the worry. This is a check Keyring makes from the ID token's `acrs` and `auth_time`; Key Vault doesn't enforce it, so a person with access can still use the CLI or portal |
| Cross-site request forgery | Every state-changing form has a per-session token checked in constant time, **and** a middleware refuses any non-GET request whose `Origin` (or `Referer`) isn't Keyring's own. Tested for every mutating route. The token is bound to the vault in the address of the page the form was rendered on, and checked against the vault in the address it is posted to. A form posted to another vault's address is refused ("You switched vaults") instead of acting on that vault |
| Open redirects after sign-in | Return paths must be local paths; absolute URLs, `//host`, backslashes and control characters fall back to `/` |
| Forged or replayed sign-in | PKCE (S256), state and nonce; ID token signature, issuer, audience and expiry checked by `openidconnect`. Sign-in state rides in an AES-256-GCM sealed cookie bound to its name |
| Cross-site scripting | Askama escapes all output, tag names and values in rows and datalists included (tested). CSP `default-src 'none'` with scripts, styles and fonts from this site only, no inline code, no `eval`. No script (`app.js`, `pins.js`, `tags.js`) uses `innerHTML` (tested) |
| A tampered pinned list | Stored entries are rebuilt from checked names and must match a local `/v/{vault}/...` path exactly, or are dropped, so editing `localStorage` can't make a link to another site, a `javascript:` URL or markup |
| Item names seen on a shared browser | Pinned and recently opened names stay in the browser's `localStorage` until cleared. Sign-out clears them, and a Clear button is under the lists. Names only: no value, version or token is ever stored |
| Clickjacking | `frame-ancestors 'none'` and `X-Frame-Options: DENY` |
| Log forging | OAuth error codes from query strings are only kept if they look like codes, and audit reason codes must be letters, digits, `_`, `.` and `-`. Free text (error strings, user agent, UPN) is logged with escaping in `text` and JSON encoding in `json`, so a crafted value can't start a new log line |
| Secret values or tokens in logs | Values and tokens live in `Secret` and `AccessToken`, which print `[redacted]`, and are zeroised when dropped. The request log has method, path, status and duration only; audit events add the person's Entra `oid`, `tid` and UPN, a keyed hash of the session ID (never the ID), the browser's address and user agent, and the vault and item names. A panic logs only its location. A test captures all `tracing` output at TRACE, in both text and JSON, during reveals, uploads, a secrets import, generation and errors and checks no value, token, password, cookie or Azure message appears |
| A PIM claims challenge used to steer sign-in | Only a challenge from ARM's own error, checked to be a small JSON object asking for `acrs` context IDs and rebuilt from the parsed value, is kept, in the session, never in a URL. The justification never goes in a URL either |
| Actions with no trace | Every audited route writes one audit event whatever the outcome, including Keyring's own refusals and Azure's 401s and 403s. A test fails on a POST route that is neither audited nor exempt with a reason |
| Values cached by browsers or proxies | `Cache-Control: no-store` on every HTML page, reveal, download and CSV |
| A typed secret's fields leaking | Every field of a Login, Database, API key or SSH key secret is part of the value and handled as one: held in `Secret`, never logged or put in an audit event, never echoed into a form after a failed check, and never carried by the reason page, which refuses to carry any create or "set a new value" form by action, not by field name. The log test puts a distinct marker in every field |
| Values left on screen or clipboard | Hidden until asked for; revealed values are wiped after 30 seconds or on leaving the page. Keyring tries to clear the clipboard if it still holds the value. After a copy, every way off the page in the same tab (Hide, Back, the nav and Sign out) waits for that clear, or a second and a half, before it leaves. Browsers only allow the clear while the tab has focus, so a clear that fails in a background tab is tried again when you come back |
| Accidental or malicious deletes | Typed-name confirmation checked on the server. Purge is refused by the server unless `KEYRING_ALLOW_PURGE=true` |
| Private key leaks | Keys: no export, backup, release, decrypt, unwrap or sign calls exist (tested); the JWK type has no private fields. Certificates: private key download only for exportable policies, after a warning and typed name. A certificate's backing secret can't be revealed, rolled back, changed or deleted through the secrets pages |
| Query injection in the audit view | Filters checked against strict patterns, then used only as escaped string literals in `let` lines. The rest of the KQL is fixed. Across vaults, the vaults' resource IDs go in the same way, one `let` line each. Keyring activity does the same, with actions checked against Keyring's own action names |
| CSV injection in exports | Fields starting with `= + - @` (and tab or CR) are prefixed so spreadsheets don't run them. The description column goes through the same guard |
| A description holding sensitive text, or disguising itself | It is a tag, readable by anyone with read access to the item's properties, so the form says not to put secrets or personal details in it. It is never logged or put in an audit event (tested at TRACE). Control and invisible format characters are refused, so it can't hide text or reorder what is shown |
| Path tricks in names | Vault, secret, certificate, key and version names are checked against Key Vault's own rules before they go in any URL. `nextLink` and backing secret URLs are only followed on the same vault, and ARM `nextLink`s on the Access page only on ARM's own host |
| Large or slow requests | Request headers must arrive within 10 seconds (slow-header clients are cut off). 64 KB body limit on forms (256 KB on the two forms that carry a secret value, 272 KB for a certificate upload of up to 256 KB, and 1040 KB for a secrets import of up to 1 MB). 90 second limit per request. At most 512 connections at once; past that, new ones wait in the listen backlog. Each connection is asked to close after 5 minutes and cut off 2 minutes later. Outbound calls have 10 second connect and 30 second total timeouts, and don't follow redirects |
| Supply chain | Few crates, all from crates.io, licence allow-list, `cargo deny` and `cargo audit` on every change and weekly, `Cargo.lock` and toolchain pinned, actions pinned by SHA, images pinned by digest, SBOM per build. No npm |
| Memory safety | `unsafe` code is forbidden in the crate |
| Container escape or tampering | Distroless static image, no shell, non-root, read-only root filesystem, no capabilities |

### Known limits

- **Sessions are in memory.** A restart signs everyone out, and several copies need sticky sessions. Anyone who can read the server's memory can read active tokens.
- **The session secret** only protects short-lived cookies (sign-in state and flash messages), which the server also refuses once they're past their age limit. Pending certificate uploads and secrets imports are kept in the server-side session. Rotating it means a restart, which signs everyone out (sessions are in memory), and cancels sign-ins in progress.
- **Step-up is Keyring's own check.** Key Vault doesn't know about it, so it doesn't stop anyone reading values with the Azure CLI, the portal or another app. It is there to raise the bar for a stolen Keyring session cookie. A Conditional Access policy on Key Vault itself is what applies everywhere. Where Entra returns `acrs` (ID token, access token or both) and the AADSTS codes for a policy that can't be met are taken from Microsoft's documentation and haven't been confirmed on a real tenant.
- **Keyring doesn't rotate credentials on the target system.** A new value set in Keyring changes Key Vault only. The rotation line on a secret's page is a display of its tags, which anyone with tag rights can write, not something Keyring checked. See [rotation.md](rotation.md).
- Keyring trusts Azure's answers. A compromised Entra tenant or Key Vault is out of scope.
- **PIM's ACRS refusal isn't documented.** For Azure resource roles, Microsoft doesn't document the body of `RoleAssignmentRequestAcrsValidationFailed`; Keyring parses the shape seen in the field and refuses anything else. Some clients also need the `xms_cc` `cp1` claim before PIM accepts an authentication context. Both are on the real-tenant checklist.
- **Access shows object IDs, not names.** Keyring has no Microsoft Graph permission, so the Access page can't name people, groups or apps, or list a group's members. It links to each in the portal instead.
- **App registration credentials aren't shown.** Client secrets and certificates on Entra app registrations would need a Graph permission, so the expiry dashboard covers Key Vault only. [app-credentials.md](app-credentials.md) points to Entra's own tools.
- **The connection cap is shared** by every client, and idle keep-alive connections and slow request bodies aren't limited beyond the 90 second request limit and the 5 minute connection age. A front-end proxy or the platform's load balancer normally covers this.
- **Pinned names outlive a closed tab.** If someone closes the browser without signing out (or their session times out), the pinned and recent names stay in that browser's `localStorage` until the next sign-out or Clear. They are names only, but on a shared computer they show what someone worked on.
- **Zeroising covers Keyring's own copies.** Copies of tokens held inside `openidconnect` and `reqwest` aren't zeroised.
- **A panic** gives that one request a 500 page. Sessions survive it, since release builds unwind.
- **Email hasn't run against a real tenant yet.** The ACS Email REST API (api-version 2025-09-01), the repeatability headers, the two-action custom role and the Bicep module are built from Microsoft's reference and tested only against a mock ACS endpoint and token service. [real-vault-checklist.md](real-vault-checklist.md) has rows for each.
- **The audit sink hasn't run against a real tenant yet.** The Logs Ingestion API, the `Direct` rule, the table and the role assignment are built from Microsoft's reference and tested only against a mock ingestion endpoint and token service. [real-vault-checklist.md](real-vault-checklist.md) has rows for each.
- **Sign-in hasn't run against a real tenant yet.** The tests use mock Entra, ARM, Key Vault and Log Analytics servers that follow Microsoft's REST reference. The Key Vault REST calls have been checked against real vaults, and `tests/real_vault.rs` repeats six of those checks on request. Sign-in, on-behalf-of, RBAC roles, the browser and deployments are still to confirm. [real-vault-checklist.md](real-vault-checklist.md) lists what has been checked.
