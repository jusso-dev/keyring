# Changelog

Notable changes to Keyring. Keyring has no releases yet, so everything is under Unreleased. Each entry names the pull request it came from. To see which commit an image was built from, read its `org.opencontainers.image.revision` label.

Releases are tagged `vX.Y.Z`, and each tag's image is built by `.github/workflows/release.yml`. The tag must point at a commit on `main` whose CI passed, match the version in `Cargo.toml`, and this file must have a `## X.Y.Z` heading for it.

## Unreleased

- **PIM role activation** (#245): when Key Vault refuses with `ForbiddenByRbac` and you're eligible for the role the 403 page names, the page offers **Activate**: a form for how long (up to PIM's maximum, checked on the server), a reason and a ticket where PIM asks, sent to PIM as you (`SelfActivate` through ARM, api-version 2020-10-01). Results in plain words: on now with Try again, waiting for approval, or refused with ARM's code. A stronger sign-in PIM asks for goes through sign-in with the checked claims challenge and back to the form. **My access** under each vault lists your Key Vault roles there, on and eligible, with time left and **Deactivate**. Keyring keeps no request state and needs no new permission; without PIM the 403 page is unchanged. New audit actions `role.activate` and `role.deactivate`, with new optional fields `role`, `role_scope` and `role_duration` (schema version 1, columns `Role`, `RoleScope` and `RoleDuration` in `KeyringAudit_CL`); the justification goes in `reason` and the ticket in `ticket`. Closes #203.
- **A reason before a value is shown** (#242): optional `KEYRING_REQUIRE_REASON` (`off`, `reveal` or `all`) and `KEYRING_REASON_TICKET_PATTERN` (a regex the ticket must match as a whole, shape only), checked at start, with `requireReason` and `reasonTicketPattern` in both Bicep templates. Keyring asks for a reason (5 to 200 characters) before a reveal or private key download, or before every change with `all`, after the form token and step-up checks and before any Key Vault call. The reason and ticket fill the audit event's `reason` and `ticket` fields, with control characters replaced so neither log format can be forged. New reason code `reason_required` (schema version stays 1). Adds the `regex` crate. Keyring's own check: the CLI needs no reason. Closes #205.
- **Sentinel content for Keyring's audit table** (#243): `infra/sentinel` adds the ASIM Audit Event parser `vimAuditEventKeyring` (and `ASimAuditEventKeyring`) for `KeyringAudit_CL`, seven analytic rules as Sentinel Scheduled rules (many reveals by one person, a reveal from a new address, one person denied in several vaults, a purge, private key download or bulk change (`*.bulk_update`) outside working hours, forged or cross-site requests, no audit events while Key Vault saw Keyring, and a Key Vault `SecretGet` with no Keyring event), hunting queries for the audit page's reports, and a workbook. Every rule is created turned off and turned on by its own parameter, with thresholds and windows as parameters and Account, IP and Azure resource entities. The two rules that need Keyring's outbound addresses aren't created without them, and the `SecretGet` rule stays off until a real vault confirms the `kv_request_id` join. With `KEYRING_AUDIT_WORKSPACE_ID` (set by both templates from `auditWorkspaceId`, checked at start), each vault's audit page gains a **Keyring activity** view of `KeyringAudit_CL`, read as you with your own Log Analytics token, with the same filters, escaping and 500-row limit; without the setting nothing changes. CI builds the template, and `tests/sentinel.rs` checks every column, action, outcome and reason code the content uses against the code. See `docs/sentinel.md`. Closes #224.
- **Change many items at once** (#244): a checkbox on each row of the secrets, certificates and keys lists and a "With selected" form to add or change a tag, remove a tag, set an expiry date (secrets and keys), enable or disable up to 100 items. A review page lists every item and exactly what will change, then a second post changes each as you, four at a time, with a results page per item (done, refused by Keyring or Azure with the role, not found, failed). Disable needs the count typed. Delete and purge stay one at a time. New audit actions `secret.bulk_update`, `certificate.bulk_update` and `key.bulk_update`, written for the request and for each item, and a new reason code, `tag_limit`. The four-at-a-time runner is shared with import (`src/routes/batch.rs`). Closes #216.
- **Pinned and recently opened** (#240): a **Pin** button (a real button with `aria-pressed`) under the heading of each vault list and each secret, certificate and key page, and **Pinned** and **Recently opened** (last 10) above everything else on the home page and vault list, when non-empty. Kept in the browser's `localStorage` under one key, holding only kinds, names and local paths (pinned capped at 50); each entry is checked to be a local `/v/{vault}/...` path before it is a link, or dropped. Signing out clears it, and there's a Clear button. A second same-origin script, `static/pins.js` (under 200 lines, no `innerHTML`, tested); the CSP is unchanged and pages are the same without JavaScript or storage. Closes #220.
- **Import secrets from a file** (#234): "Import secrets" on the secrets list reads a `.env` or CSV file (`name,value`, optional `content_type`, `expires`, `tags`), up to 500 rows and 1 MB, converts names to Key Vault's rules and refuses names that clash, and shows a preview of every name and whether it is new, a new version or blocked by a deleted secret, never a value. Import writes each secret as you, four at a time, with a results page per row. The file waits in the server-side session for up to 10 minutes and is zeroised when dropped. A new audit action, `secret.import`, is written for the request and for each secret written. There is no export. Closes #217.
- **Permission hints** (#238): a button your roles don't allow (Set a new value, Edit details, Delete, Disable, Enable, Show value, Rotate now, Create, Upload, Recover, Permanently delete) stays visible but disabled, with the role it needs beside it ("Needs Key Vault Secrets Officer"), the same role the 403 page names. Read from ARM's `permissions` call as you, at the item's own scope on item pages, kept in the session for five minutes. Only a hint: Key Vault still decides and the forms are unchanged. Every button stays enabled if ARM fails, is slow (2 second limit) or the vault uses access policies. Closes #207.
- **App registration credentials** (#241): `docs/app-credentials.md` says why Keyring doesn't show client secrets and certificates on Entra app registrations (it would need a Graph permission Keyring doesn't ask for) and what to use instead: Entra's expiring-credential recommendations, SAML certificate emails, a read-only `az ad app list` query, and managed identities or federated credentials so there is no secret to expire. The expiry dashboard gains one line saying it covers Key Vault only, with a link. No new permission, call or setting. Closes #219.
- **Used by in the last 30 days** (#236): each secret, certificate and key page, and Set a new value, Roll back, Disable, Rotate and Delete, list the people, apps and managed identities that read the secret (or the certificate's backing secret) or signed, wrapped, decrypted and so on with the key, from Key Vault's audit log: kind, name or app ID, object ID, last use, count, client info and IP. One summarised query per workspace, as you, within its own 5 second limit beside the page's other reads. It's advice: if the log can't be read the panel says why and the action still goes ahead. Closes #214.
- **Audit sink** (#237): Keyring's own audit events can also go straight to a `KeyringAudit_CL` table in Log Analytics through the Logs Ingestion API (`KEYRING_AUDIT_INGESTION_ENDPOINT`, `KEYRING_AUDIT_DCR_ID`, `KEYRING_AUDIT_STREAM`), written only as Keyring's managed identity, with each row naming the person who acted and the writer. Batched, gzipped, retried, with a bounded queue, a shutdown flush and `/healthz/audit`. `KEYRING_AUDIT_REQUIRED` refuses reveals and private key downloads while the sink is degraded. `KEYRING_MANAGED_IDENTITY_CLIENT_ID` is now the one identity setting; `KEYRING_FEDERATED_IDENTITY_CLIENT_ID` still works for one release, with a warning. The templates take `auditWorkspaceId` (`infra/modules/audit-sink.bicep`). Closes #223.
- **Rotation status from tags** (#239): a secret's page shows one line from its `rotation`, `rotation-last` and `rotation-status` tags ("Rotated by storage-key-rotator, last 2 Nov 2026, OK"), marked as what the tags say rather than something Keyring checked, with anything off-format shown as unknown. The expiry dashboard gains a **Rotation failed** table from the tags its list calls already return. No new Azure calls and no rotation code: `docs/rotation.md` explains Azure's own pattern, removing the credential instead, and the tag convention. Closes #218.
- **Step-up before sensitive actions** (#235): optional `KEYRING_STEP_UP_AUTH_CONTEXT` (a Conditional Access authentication context, `c1` to `c99`) and `KEYRING_STEP_UP_MAX_AGE` (minutes since sign-in), with `stepUpAuthContext` and `stepUpMaxAge` in both Bicep templates. Before a reveal, private key download, rollback or purge, Keyring checks the `acrs` and `auth_time` it kept from the ID token, and if they fall short says "Your organisation asks you to confirm it's you before showing values." and sends the person to Entra with the `claims` parameter (or `prompt=login` and `max_age`), back to the confirmation step. A step-up sign-in that returns without it is refused without looping. New audit reason codes `step_up_required` and `step_up_not_met` (schema version stays 1). Keyring's own check: Key Vault doesn't enforce it. Off by default. Closes #204.
- **Access** (#233): each vault has an Access page, and each secret, certificate and key page an Access section, showing who can reach it: Azure role assignments at the item, vault, resource group, subscription or above, PIM eligible ones, and on older vaults the access policies in plain words. Only roles that reach the contents are listed, plus Owner, Contributor and User Access Administrator flagged as able to grant themselves access. People, groups and apps are shown by object ID and type with a portal link; names aren't looked up, so no Microsoft Graph permission is needed. CSV export, a plain explanation when you can't read role assignments, and a 5 second limit on item pages. Read through ARM as you, with Reader enough. Closes #206.
- **Age view**: `/expiry/age`, beside the expiry dashboard, groups every secret, certificate and key across your vaults by how long since its value last changed (under 90 days, 90 to 180, 180 to 365, over a year), from the current version's created date, with CSV export and the vaults it couldn't read. The secrets list gains a "Value changed" column and a "Not changed in over N days" filter, and `KEYRING_STALE_AFTER_DAYS` (default 365, checked at start; `staleAfterDays` in the Bicep templates) sets when a "Not changed in over a year" badge shows on lists and pages. Certificate-backed secrets and keys are left out. Reads the shared list cache, never a value. Assumes the list calls give the current version's created date, still to confirm on a real vault. Closes #210 (#230).
- **Keyring's own audit events** (#232): every reveal, private key download, change, delete, recover, purge, sign-in, failed sign-in, sign-out and session expiry writes one structured event through `audit::record` (`src/audit.rs`), schema version 1, for every outcome: `success`, `denied` (Azure 401 or 403), `refused` (Keyring's own check, with a fixed reason code) or `failed`. Events carry who (`actor_oid`, `actor_tid`, `actor_upn`), a keyed `session_ref`, the browser's `client_ip` and `user_agent`, what was acted on, and `kv_request_id`, the new `x-ms-client-request-id` Keyring sends on each Key Vault call. `KEYRING_LOG_FORMAT=json` writes every line as JSON with audit events marked `"kind":"audit"`; `KEYRING_TRUSTED_PROXY_HOPS` (default 0, 1 in the templates) reads the browser's address from `X-Forwarded-For`. The free-text action lines (`secret value revealed` and the rest) are gone, so KQL that matched them needs the new queries in `docs/deploy.md`. A test fails on any POST route without an event. Closes #222.
- **Audit across vaults** (#229): `/audit` with no vault runs fixed reports over every vault you can see: secret values read, private keys downloaded, deletes, purges and recoveries, refused requests by person and vault, and one person's activity. Vaults sharing a Log Analytics workspace are covered by one query, as you. Up to 500 rows, CSV export, and vaults or workspaces that couldn't be read are listed. Rows link to the vault's own audit page. #212.
- **Vault health page**: `/vault-health` checks every vault you can see for audit logs, Azure RBAC, soft delete, purge protection, network access, private endpoints and secrets without expiry, as Pass, Warn or Unknown, never a guessed pass. Pick one vault to also check certificate renewal and key rotation, which need a call per item. Each warning says what to do and links to Microsoft's guide, there is a CSV export, and the vault list gains an Audit logs column with a warning badge when they're off. Reader is enough for every check except the content counts (Key Vault Reader). Closes #211 (#228).
- **Search across vaults**: a search box in the top bar, and `/search?q=...`, find secrets, certificates and keys in every vault you can see by name, tag or content type (case-insensitive), with filters for type, vault and status. Results are grouped by vault with the usual status badges, and vaults that couldn't be read are listed with the reason. Only list calls are made, never a value. Each vault's list is kept in the session for a minute, shared with the expiry dashboard, so a second search doesn't read every vault again. Works without JavaScript. #209 (#227).
- **Access alerts** (#226): `infra/alerts/access.bicep` adds optional Azure Monitor alerts for a read of a watched secret, any purge, and more than N refusals from one caller in 15 minutes, with who, what and IP but never a value. Azure runs them; Keyring is unchanged. See `docs/alerts.md`. #213.
- **Shared vault fan-out**: reading every vault the person can see (six at a time, 20 seconds each, a minute in all, with the vaults not read and why) moves out of the expiry dashboard into `src/azure/fanout.rs`, ready for cross-vault search. No change in behaviour. Part of #209 (#225).
- **Clipboard cleared on every way out**: after Copy on a revealed secret or a generated value, Back, the side nav, the top bar and Sign out now wait for the clipboard clear (or a second and a half if the browser is stuck on a paste prompt) before they leave, as Hide already did. Before, only Hide waited, and a clear started as the page closed could be cut off. Links that open a new tab or stay on the page aren't held up.

- **IBM Plex type**: the UI is set in IBM Plex Sans, with IBM Plex Mono for names and values, in place of the system fonts. Keyring serves the four font files itself (about 90 KB, SIL Open Font License), so the CSP only gains `font-src 'self'`.
- **Operational console look**: the web UI is restyled as a calm operational console with ledger-style tables, from a locked design system in `design.md` (OKLCH tokens with every contrast ratio worked out). Status badges always have a label and a glyph, the reveal page shows the value in a bordered well with a text countdown and a note that the read is recorded, and the expiry page opens with count tiles. Visual only: routes, forms and script behaviour are unchanged, and the README screenshots are retaken.

- **Managed identity credential**: Keyring can prove itself to Entra with the app's managed identity (`KEYRING_FEDERATED_IDENTITY_CLIENT_ID`) instead of a client secret, so there is no secret to rotate. `ENTRA_CLIENT_SECRET` is now optional, and the Bicep templates have `useFederatedCredential`. The app registration must stay delegated-only (see the threat model).

- **Certificate renewal**: a certificate's page has a "Change" link next to "Near expiry". It opens a form to renew automatically or email the vault's contacts, with a number of days, and saves it with `PATCH /certificates/{name}/policy`. "Do nothing" is only offered when the certificate has no action yet, because a real vault keeps the old action when sent an empty list.

- **Release workflow checks CI first**: a version tag must point at a commit on `main` whose four required CI checks passed, or the release workflow stops before building. It only repeats CI's image checks, so this keeps a tagged image from skipping the Rust and supply-chain checks.

### Review fixes, November 2026

A code review on 10-11-2026 filed issues #73 to #173 (index #174). These are the fixes so far, one line per area. Each issue says what was wrong.

- **Sign-in and sessions** (#181): the callback checks `state` before it trusts an `error=` reply, sealed cookies are time-limited on the server, sign-in metadata is fetched once and kept as a fallback, Entra errors are sorted in one place, the `.env.example` placeholder is refused as `SESSION_SECRET`, and expired sessions are swept every minute. #73, #74, #76, #77, #78, #80, #81, #82, #83, #84.
- **Tokens** (#181): concurrent requests share one refresh and one on-behalf-of exchange per resource, and share a failure too. #75.
- **Server** (#181): a request log line per request, a warning at start for any test-only override, at most 512 connections each closed after 5 minutes, unwinding panics that give one 500 page instead of ending every session, and the HTTP client built before binding. #79, #85, #86, #87, #88.
- **Forms** (#179, #181): every changing form is bound to the vault it was opened for, and the form token is checked before Azure is called. #89, #108.
- **Secrets** (#179): multi-line values are kept as typed, rollback keeps the enabled state and expiry, edits go to the version that was shown, tags round-trip, start and expiry times keep their minutes, the delete warning gives the vault's real retention period, and purge isn't offered on purge-protected vaults. #90, #91, #92, #93, #100, #101, #104, #105, #106, #107, #111, #113.
- **Reveal and copy** (#177): Keyring tries to clear the clipboard and retries when you come back to the tab, the auto-hide holds in background tabs, hidden buttons stay hidden, pages reflow at 320 pixels, and the idle sign-out gives a warning. #94, #95, #134, #135, #136, #140, #141.
- **Expiry, audit and errors** (#178): the expiry dashboard has time limits per vault and overall and lists what it couldn't read, the audit view says which workspaces it left out, a 409 for a soft-deleted name says so, and static files are versioned and cached for a year. #96, #97, #98, #102, #103, #109, #110, #112.
- **Certificates** (#180): the issuer is a select of Self and the vault's own issuers, pending requests can be cancelled, self-signed creates show "Being created", uploads show the leaf certificate and say when a name exists, PEM keys must be PKCS #8 and match, BER PFX files can be uploaded, and certificates can be enabled and disabled. #114, #116, #117, #118, #119, #120, #123, #125, #127, #128, #130, #131, #132.
- **Keys** (#180): the rotation policy form keeps what it can't show and Key Vault's own durations, checks Key Vault's limits, and reads the default policy as none. Managed keys are refused on the server, and keys can be enabled and disabled. #115, #121, #122, #126, #129.
- **Azure's message** (#180): a 400 on a write shows Key Vault's own reason under the form, cut to 500 characters and never logged. #124.
- **Deployment, CI and docs** (#176): internal Container Apps ingress with private DNS, App Service logs to a workspace, the alerts topic in the vault's region, image labels, a CI check that docs only name `src/` files that exist, and many doc corrections. #151, #153, #154, #155, #157, #158, #159, #160, #161, #163, #164, #165, #166, #167, #168.
- **Docs and tests** (#182): the architecture, deploy and troubleshooting pages describe the fixes above, the README says which certificate issuers Keyring supports, `docs/real-vault-checklist.md` lists what the first real-tenant run must confirm, and a test checks the numbers in the docs against the code. #119, #124, #169, #170, #171.
- **Shared code** (#183): one form token check, field errors and name check for every form; delete, recover and purge written once for secrets, certificates and keys; fixed pages moved under `/-/` (old addresses redirect); the deleted lists are paged; dead code and stale comments removed. #99, #133, #172, #173.
- **Templates and accessibility** (#184): shared partials for fields, tables and confirm pages, row actions kept inside table cells, wide tables reachable by keyboard, focus moved to the error summary or message, and disable asks first. #137, #138, #139, #142, #143, #144, #145, #146, #147, #148, #149, #150.
- **Deleted pages** (#185): secrets use the shared deleted list and deleted page too, which keep a secret's content type and now give every kind the vault's real retention period. #150, #172.
- **Visibility** (#186): `unreachable_pub` is on, so items only the crate uses are `pub(crate)` or `pub(super)` and the compiler reports them when they fall out of use. That found and removed a few more unused items: two never-read Azure fields, an unused key name helper, and two checks used only by their own tests. #173.
- **Vault in the address** (#188): item addresses now name the vault (`/v/kv-prod/secrets/db-password`), so links can be shared and two tabs can hold different vaults. The form token is still bound to a vault and is checked against the vault in the address. Old addresses redirect to the vault last used, and the expiry dashboard's "Open" is a plain link.
- **First real-vault run** (#187): Key Vault keeps a version's start and expiry dates when sent `null`, so the secret edit form now refuses a removed date and says to set a new value instead of reporting a change that didn't happen. An HSM key on a Standard vault is refused with 403 `HardwareKeysNotSupported`, not 400, so Keyring now matches that code. The mocks follow both, and `docs/real-vault-checklist.md` records the results. #129, #170.
- **Managed identity follow-ups** (#194): a request queued behind a failed identity token fetch now gets that failure instead of starting another, so an outage costs one timeout. Container Apps can move an existing app to the managed identity in two deployments (`keepClientSecretEntry`). The deploy guide covers redeploying App Service with `useFederatedCredential` and removing an old identity's federated credential.
- **Repeatable real-vault run** (this change): `tests/real_vault.rs` runs six checklist rows against a throwaway `kr-test-` vault when asked, and against the mock on every `cargo test`. Its first run found that Key Vault refuses a POST with no `Content-Length` (411), which broke recover for secrets, keys and certificates. Keyring now sends `Content-Length: 0`, and the mock refuses such a POST too. The mock's 409s match Key Vault's inner codes.

### Security

- `deny.toml` also bans `aws-lc-rs` and `aws-lc-sys`, so a dependency change can't quietly swap rustls's ring provider for aws-lc.
- CI installs its tools only from pinned, checksummed binaries (no fallback download), pins the Bicep CLI, and pins the Dockerfile build frontend by digest.

### Deployment

- Container Apps with `ingress = 'internal'` is reachable from the VNet. The template outputs `defaultDomain` and `staticIp` and can create the private DNS zone (`privateDnsVnetId`).
- Both templates take `apiScope` and `logLevel`.
- App Service can send Keyring's output to Log Analytics (`logAnalyticsWorkspaceId`), and otherwise keeps a 7 day local log.
- The alerts template puts the system topic in the vault's region and can use a topic the vault already has (`existingSystemTopicName`).
- Images carry `org.opencontainers.image.version` and `org.opencontainers.image.revision` labels.

### Documentation

- App registration: the Log Analytics API permission and the sign-out redirect URI.
- Role table: the smallest role first, and which roles can read secret values.
- Rotating the client secret and `SESSION_SECRET`, logs on each platform, proxies and private CAs, and more troubleshooting rows.
