# Changelog

Notable changes to Keyring. Keyring has no releases yet, so everything is under Unreleased. Each entry names the pull request it came from. To see which commit an image was built from, read its `org.opencontainers.image.revision` label.

Releases are tagged `vX.Y.Z`, and each tag's image is built by `.github/workflows/release.yml`. The tag must point at a commit on `main` whose CI passed, match the version in `Cargo.toml`, and this file must have a `## X.Y.Z` heading for it.

## Unreleased

- **README rewritten** (#283, #262 and part 4 of #261): a plain intro saying what Keyring is for; a status line saying what is tested against mocks, what the real-tenant browser run on 17-11-2026 covered (its two findings, #250 and #251, fixed) and what is still unconfirmed, with a link to the checklist; "What it does" in groups (find and use secrets, control, audit and compliance, lifecycle, notifications, operations), each line linking to its doc; a "What covers what" table by capability, marking each Key Vault, Keyring, Azure or Not covered; an "Apps and pipelines" section pointing to Key Vault's own paths for machine access and saying why Keyring adds no API; and Configuration as grouped tables with a default for every setting. `tests/docs.rs` now checks the README has a row for every `KEYRING_*` setting in `src/config.rs` (test-only overrides left out) and has no hype words or em dashes. Final pass: lines for access requests, activity emails, reveal limits, the access review and sharing a secret (off by default; without PIM a share is a plain assignment Azure doesn't end on its date); rows for `KEYRING_NOTIFY_OWNER_ON_READ`, `KEYRING_EVENTGRID_SUBSCRIPTIONS`, `KEYRING_SHARING` and `KEYRING_SHARE_MAX_DAYS`, and the two Microsoft Graph permissions sharing needs; the managed identity's email role under How access works; the notify list in the bulk change line; and a Documentation section linking the docs site, design document, guides and administrator SOPs. Closes #262 and #261.
- **Reveal limits** (part 2 of #261): a `keyring-reveal` tag on a secret or certificate, set with a new Reveal limit select on a secret's forms and a certificate's Edit details (not keys). `copy-only` hides Show value: Copy still works with clipboard clearing, the value is only in hidden form fields (off the screen, not out of the browser). `none` refuses reveal, Copy and copy to another vault. On a certificate any limit refuses the private key download; the public certificate stays. Any other value, or the name in another case, counts as `none`, is shown with a note and kept. Checked on the server, from properties before step-up and the reason gate so no value is read when the limit is already set, and again on the value response; an old version follows the stricter of its own and the current version's limit. Rollback, Set a new value, Edit details, import, certificate upload and copy to another vault (whatever is ticked) carry the stricter limit onto the new version; tag rows, import files and the bulk change refuse the tag name. Loosening it needs the same step-up (when step-up is set up) and, with `KEYRING_REQUIRE_REASON=reveal`, reason as a reveal. New `reason_code` `reveal_limited`, and optional audit fields `reveal_limit_from` and `reveal_limit_to` (schema version stays 1; columns `RevealLimitFrom` and `RevealLimitTo`). A Keyring control: the CLI, portal and SDKs aren't limited.
- **Request access when PIM isn't available** (#258): with email on and `access-requests` in `KEYRING_NOTIFY_TYPES`, a Key Vault 403 page that offers no PIM Activate, and My access, offer **Request access** for the role the page names, for one item or the whole vault, with a reason and an optional ticket. Keyring emails the vault's `keyring-owners` (or `KEYRING_NOTIFY_ADMINS`) with a copy to the requester's own sign-in name, links to the vault's Access control page in the portal, keeps no request and grants nothing. One request per person, vault and role an hour. The email quotes the reason and ticket only when a mail client couldn't turn them into a link. New audit action `access.request` and reason code `rate_limited`.
- **Activity emails** (#259): with `watched-reads` in `KEYRING_NOTIFY_TYPES`, a successful reveal, private key download, copy read or rollback emails the item's `notify` addresses (and its `owner` with new `KEYRING_NOTIFY_OWNER_ON_READ=true`), from the tags Keyring already read. With `destructive`, a delete, purge or bulk change emails the vault's `keyring-owners` (or `KEYRING_NOTIFY_ADMINS`), one email per bulk request listing up to 50 names. With `role-use`, a PIM role turned on or off emails the vault's owners with the role, scope and duration. The person who acted isn't emailed unless they are the only address. Never a value, reason, justification, description or tag value: the email says a reason was given. At most 4 watched-read emails an hour per item. Works with the audit sink off. Closes #259.

- **Expiry webhook: allow-list of subscriptions** (#280): new optional `KEYRING_EVENTGRID_SUBSCRIPTIONS`, subscription IDs separated by commas (at most 50, any case, kept once), checked at start; an entry that isn't a GUID, an empty entry or more than 50 stops Keyring naming the setting, never the value, and it is refused without the ACS endpoint or without `expiry` in the types. When set, an event on `/hooks/eventgrid` from a Key Vault in a subscription that isn't listed refuses the whole delivery with 400 and new reason code `subscription_not_allowed`, checked with the `topic` after the token and before dedupe or email; a `topic` that isn't a Key Vault ID is still `bad_topic`. Nothing from `topic` is logged, audited or emailed. Unset keeps today's behaviour, with one `warn` line at start. The App Service and Container Apps templates gain `eventGridSubscriptions`, default the deployment's own subscription, set when `expiry` is in `notifyTypes`. Closes #278.
- **Access review** (part 3 of #261, #279): a page and CSV per vault, `/v/{vault}/access/review`, reached from the Access page. One row per secret, certificate and key with type, enabled, expiry, owner, notify, description, when the value last changed, who used it in the last 90 days, who has access to it (vault-wide once above the table, item-scoped on each row, and a complete capped column in the CSV) and its rotation status from the cleaned rotation tags. "Used by" here is one Log Analytics query per workspace for every item, with the same vault-events row and outcome rule as the panel, at most 20 callers per item and 2000 rows per workspace, said when reached. Every gap (no diagnostic setting, an unreadable workspace or role assignments, no events yet, a partial answer, a failing or slow read) is said once at the top and marks each affected cell "Not known", on the page and as `NOT READ` rows in the CSV. Reads only, as the person; no value, no new permission, no audit event of Keyring's own.
- **Owner and notify tags** (#255, #277): who each secret, certificate, key and vault belongs to, kept in tags so Keyring stores nothing. Owner and Notify fields sit after Description on secret create, edit and set value, certificate create and upload, key create, and Edit details for certificates and keys, kept in the item's reserved `owner` tag (one address) and `notify` tag (up to 5 addresses separated by commas, within the tag's 256 characters). Each address is parsed with `notify::Address`, must be in `KEYRING_NOTIFY_ALLOWED_DOMAINS` when that is set, and a refusal names the entry by place without quoting it. An empty field removes the tag; both count towards the 15 tags and are merged into the others. A value set in the portal or the CLI that Keyring wouldn't write is shown as it is with a note, and kept byte for byte while its field is left as the form showed it, so it never blocks another change. The owner shows on each item's page and in an Owner column on the lists, search, the import preview and the expiry and age pages, notify on each item's page, both in the expiry and age CSVs (formula guarded); an address that parses is a `mailto:` link, percent-encoded as RFC 6068 asks, anything else plain text. The tag filter on every list and on the expiry and age pages, the search box, the live filter and the cross-vault search still find `owner` and `notify` like any tag (`notify=<address>` matches any one entry); the filter boxes never suggest them. A tag such as ` owner ` set in the portal is kept on save; adding one is refused. **Owned by me** on the three lists matches the signed-in UPN against `owner` or any `notify` entry, ignoring case, and posts only `mine=1`. The bulk change can set or remove each; the import reads optional `owner` and `notify` columns; copy brings them with the tags; search matches the owner and notify addresses; the Owner field suggests owners used in the vault (up to 50). The tag rows, tag suggestions, CSV `tags` column and bulk tag change refuse `owner` and `notify` as tag names. New optional `KEYRING_REQUIRE_OWNER=true` (Bicep `requireOwner`) refuses every form save that leaves an item without an owner, skips import rows without one, refuses a copy that wouldn't bring one and the bulk **Remove the owner**, all with new `reason_code` `owner_required`; rotate, rollback, enable, disable and renewal aren't checked, and the CLI and portal aren't limited. The vault list and vault health show the vault's `keyring-owners` ARM tag from the Resource Graph query Keyring already makes, and a new **Owners** health check warns when it is missing, empty or holds no address, saying to set it in the portal's Tags blade or with `az tag update` (Keyring never writes vault tags). `owner::item_recipients` and `owner::vault_owners` give the later access request (#258) and activity (#259) emails their recipients; no email is sent here. Addresses are never logged or put in an audit event or a flash message, and Keyring never builds a URL with one in it; typing `owner=<address>` into a filter puts it in the person's own query string, which Keyring never logs (tested at TRACE). Closes #255.
- **Tag rows and suggestions** (#253): every form that sets tags (secret create, edit and set value, certificate create and upload, key create, and Edit details for certificates and keys) has a row per tag, a name input and a value input, in place of the `name=value` box, with three empty rows so it works without JavaScript. Names and values now keep `=` and spaces exactly, so only tags with a line break are still listed and kept as they are. Rows post as `tag-name-n` and `tag-value-n` (up to 40); each error shows beside its row, with the same limits as before (15 tags with the description, 512 and 256 characters, a name once, `description` reserved). `<datalist>` suggestions of the names and values already used in the vault, most used first, read as you from the vault's lists through the per-session list cache within 2 seconds, never a value or the description, capped at 200 names and 50 values per name. The list filters, vault list, expiry, age and search boxes suggest `name` and `name=value` from the page; certificates and keys get a tag filter; each tag on an item's page links to the filtered list. New optional script `static/tags.js` (under 150 lines, tested) swaps a row's value list and adds or removes rows. Import and copy are unchanged. Closes #253.
- **Password policy for typed values** (#275, part 1 of #261): optional `KEYRING_PASSWORD_POLICY` (for example `min=14,upper,lower,digit,symbol,max-repeat=3,common`; Bicep `passwordPolicy`) checks a value typed into a Password secret or a Login's password field when it is created or given a new value. Rules: fewest characters (counted in characters, not bytes), upper case, lower case, digit, symbol, most of one character in a row, and not on a built-in list of 1,000 common passwords (from SecLists, MIT licence). The form says what the policy asks for before anyone types; a value that misses gets a field error naming the rule, never the value. Import from a file checks each value it would write and skips a row that misses, naming it in the preview; it now refuses a row with a Keyring content type (`application/vnd.keyring.`), policy or not, so it can't make a Login or other typed secret. Every rule runs on the visible characters only (letters, numbers, punctuation, symbols and spaces): invisible characters, combining marks, line breaks and unassigned code points don't count towards `min`, aren't a symbol or a letter, don't break up a run for `max-repeat` and don't hide a common password. A refusal is audited with `reason_code` `password_policy`. Unset means no policy. A bad setting stops Keyring at start. Other types, copy and rollback aren't checked, and the CLI and portal aren't limited by it.
- **Expiry emails pushed by Event Grid** (#274): `POST /hooks/eventgrid` takes Key Vault's six `*NearExpiry` and `*Expired` events and emails each through ACS, without reading any vault (Keyring's identity has no vault access). Every delivery needs an Entra token: RS256, signed by the tenant's keys from the sign-in cache (a new key refetched at most once every 5 minutes, whatever the token claims), the tenant's v1 or v2 issuer, `aud` equal to the new `KEYRING_EVENTGRID_AUDIENCE` or `api://<client ID>`, the tenant's `tid`, `exp` and `nbf`, Event Grid's application in `appid` or `azp`, the `AzureEventGridSecureWebhookSubscriber` app role, and no `scp`. 401 with no body on any failure, 404 unless `expiry` is on, 1 MB, 50 events, JSON and POST only. The token is checked first: 120 deliveries a minute with a good token, and a separate counter of 60 a minute for bad tokens, past which they get 429 with no audit event (one `warn` line a minute counts them), so a flood of bad tokens can't block Event Grid. Each event's `topic` must be the resource ID of the Key Vault it names (Event Grid stamps it; a custom topic's events carry their own ID), else 400 `bad_topic`. All or nothing: one malformed event refuses the delivery with 400. Emails hold only checked names, the version and the expiry date Keyring formats, with links to the item and the expiry dashboard. Recipients: the subscription's `keyring-notify` header only when `KEYRING_NOTIFY_ALLOWED_DOMAINS` is set, otherwise `KEYRING_NOTIFY_ADMINS`. Deduplicated per item, version and event type for 24 hours in a bounded map (full means 503, never a repeat). 503 when the email queue is full, or when every recipient is over `KEYRING_NOTIFY_RATE_PER_HOUR` (new `Enqueued::RateLimited`, reason `recipient_rate_limited`), so Event Grid retries; an email that reached some recipients counts as sent. The Origin check skips exactly this one path. New audit action `notify.webhook` with optional field `notify_event_count` (schema version stays 1; column `NotifyEventCount`). `infra/alerts` gains `notifyVia = 'actionGroup' | 'keyring'`, with Entra auth, the delivery header and dead-lettering; the one-off Entra steps are in `docs/alerts.md`, which now tell deployers to remove their own app role assignment once the subscription exists. Closes #257.
- **Health emails to the admins** (#273): with `health` in `KEYRING_NOTIFY_TYPES`, Keyring emails `KEYRING_NOTIFY_ADMINS` when the audit sink has been degraded for five minutes and again when it recovers (with drop counts), when one person or one address has more than `KEYRING_NOTIFY_BURST_THRESHOLD` (default 20) refused or denied requests in 15 minutes (naming them, the count and the reason codes, with a link to their activity), and at 30, 14, 7 and 1 days before `KEYRING_CLIENT_SECRET_EXPIRES` and once it has passed. One email per incident; email failing is logged once and shown on `/healthz/notify`. New settings: `KEYRING_NOTIFY_BURST_THRESHOLD` and `KEYRING_CLIENT_SECRET_EXPIRES` (refused at start when malformed, or when no client secret is in use). Refusals are counted in memory through a new audit observer (`audit::Observe`), so this works with the audit sink off.
- **Descriptions on secrets, certificates and keys** (#267): a Description field (up to 256 characters, line breaks kept, with a count of characters left) on secret create, edit and set value, certificate create and upload, and key create, kept in the item's reserved `description` tag, so Keyring stores nothing and the portal and CLI see it too. It is merged into the other tags, never written over them; an empty field removes it; a sixteenth tag is refused before Key Vault is called. The length is counted in UTF-16 code units, as Key Vault and the browser count it, and control and invisible format characters are refused with the reveal reason's checks. New **Edit details** for certificates and keys changes the description and tags of the current version with `PATCH /certificates/{name}/{version}` or `PATCH /keys/{name}/{version}`, sending tags only, as you; new audit actions `certificate.update` and `key.update`. The description shows under each item's heading, in a Description column on the lists, search results and import preview, and in the expiry and age CSV exports (formula guarded). Search and list filters match it, the import reads an optional `description` column, the bulk change can set or remove it, and copy brings it with the tags. The tags box hides `description` and refuses it as an ordinary tag name. The note is never logged or put in an audit event (tested at TRACE). A "Well-known tags" section in the README and `docs/architecture.md` lists it. Closes #254.
- **Supply chain: one advisory accepted** (#272): RustSec marked `chrono` unmaintained on 17-11-2026 (RUSTSEC-2026-0543, a notice, not a vulnerability). It is in the tree through `openidconnect` and `oauth2`, which have no release without it, so `deny.toml` and `.cargo/audit.toml` ignore that one ID, with the reason. #271 tracks removing it.
- **Email through Azure Communication Services** (#266): the sender for email notices, sent as Keyring's managed identity with a token for `https://communication.azure.com`, never an access key or connection string. Settings `KEYRING_NOTIFY_ACS_ENDPOINT` (HTTPS on `communication.azure.com` only, and refused without the managed identity), `KEYRING_NOTIFY_SENDER`, `KEYRING_NOTIFY_TYPES` (`expiry`, `access-requests`, `watched-reads`, `destructive`, `role-use`, `health`; none by default), `KEYRING_NOTIFY_ADMINS`, `KEYRING_NOTIFY_ALLOWED_DOMAINS`, `KEYRING_NOTIFY_RATE_PER_HOUR` (default 20 per recipient per type) and `KEYRING_NOTIFY_AUDIT_RECIPIENTS`, all checked at start. ACS Email api-version 2025-09-01, with repeatability headers reused on every retry and no retry under a new ID after ACS's five-minute window; results polled at most three times; the poll address must be on the endpoint's own host before the token is sent. New audit actions `notify.sent` and `notify.failed` with optional fields `notify_type`, `notify_recipient_count` and `notify_recipients` (schema version stays 1; columns `NotifyType`, `NotifyRecipientCount` and `NotifyRecipients`). `/healthz/notify` like `/healthz/audit`. `infra/modules/notify.bicep`, used by both templates when `notifyDomain` is set, makes the Email Communication Service, domain and Communication Services resource in Keyring's own resource group and a custom role with only `CommunicationServices/Read` and `Write` on that one resource, assigned straight to the identity. Notices themselves come in later changes. Closes #256.
- **"Used by" no longer calls an empty log safe** (#264): the panel said "No reads in the last 30 days, so nothing should break" when a new diagnostic setting hadn't sent any events yet. It now says "No secret reads found in the available logs for this period. Logs may be delayed or incomplete; check consumers before changing this secret." (key use for a key, certificate private-key access for a certificate), and tells apart callers found, a complete empty answer, no events from the vault yet or a missing table (unknown history, with what to ask for), a workspace you can't read, and some workspaces failing or a partial answer. Every state shows which workspaces and period were looked at and what the log can't show. The change form still works whatever the panel says. Closes #251.
- **Audit no longer calls accepted requests refused** (#265): Key Vault answers a certificate create with 202 Accepted, and the audit page and the reports across vaults showed it as "Refused (Accepted)". One rule now decides every audit outcome, on the page, in both CSVs, in the reports' KQL and in "Used by": the HTTP status wins, 2xx is Allowed (202 is Accepted), 401 and 403 are Refused, other 4xx and 5xx are Failed, and a missing or unknown result stays Unknown. The query reads the status and `ResultType` from both `AZKVAuditLogs` and `AzureDiagnostics`. The CSVs gain an Outcome column. Keyring's own `certificate.create` event already recorded a 202 as success; a test now pins it.
- **My access accuracy and the audit schema rule** (#249): My access reads each PIM instance's start time as well as its end, so a role assigned to start later is listed under **Starting later** with its start time and no Deactivate, an eligibility that starts later offers no Activate (on My access, the 403 page or the form), and one with a time Keyring can't read isn't shown, with a note. A failed read of waiting requests now says so, and waiting requests are listed from the requests themselves, so they still show when the eligible roles can't be read. The audit schema stays at version 1: adding an optional field keeps the version, renaming or removing one or changing its meaning or type needs a new one, and `tests/audit_events.rs` now pins the version 1 fields and lists the ones added since. Closes #248.
- **Copy a secret to another vault** (#247): "Copy to another vault" on a secret's page picks a target vault from the ones you can see, a name (the same by default) and what to bring (content type, tags, dates, enabled), then reviews: both vaults named, new or new version, and a soft-deleted target name stops it. The copy reads the value with `getSecret` in the source and writes it with `setSecret` in the target, both as you; the value passes through memory only and is never shown. Guarded like a reveal: form token, `KEYRING_AUDIT_REQUIRED`, step-up and `KEYRING_REQUIRE_REASON=reveal`. Two new audit actions, `secret.copy.read` (source) and `secret.copy.write` (target), each with its own vault, name and outcome; the Sentinel parser maps them to `Read` and `Set`. Certificate backing secrets are refused.
- **PIM role activation** (#245): when Key Vault refuses with `ForbiddenByRbac` and you're eligible for the role the 403 page names, the page offers **Activate**: a form for how long (up to PIM's maximum, checked on the server), a reason and a ticket where PIM asks, sent to PIM as you (`SelfActivate` through ARM, api-version 2020-10-01). Results in plain words: on now with Try again, waiting for approval, or refused with ARM's code. A stronger sign-in PIM asks for goes through sign-in with the checked claims challenge and back to the form. **My access** under each vault lists your Key Vault roles there, on and eligible, with time left and **Deactivate**. Keyring keeps no request state and needs no new permission; without PIM the 403 page is unchanged. New audit actions `role.activate` and `role.deactivate`, with new optional fields `role`, `role_scope` and `role_duration` (schema version 1, columns `Role`, `RoleScope` and `RoleDuration` in `KeyringAudit_CL`); the justification goes in `reason` and the ticket in `ticket`. Closes #203.
- **Secret types with several fields** (#246): when you create a secret, choose Password (one value, as before), Login (URL, username, password, notes), Database (server, database, username, password), API key (key, endpoint, notes) or SSH private key (username, host, private key, passphrase). The value is compact JSON built by serde_json, with the content type `application/vnd.keyring.<type>+json;v=1`, so other tools see an ordinary JSON string. Every field is part of the secret value: each is held as a `Secret`, never logged, put in an audit event or echoed back into a form, and showing any of them is a reveal (`secret.reveal`). The reveal page shows each field with its own Copy and the same clipboard clearing, and, for Database, SQL Server and PostgreSQL connection strings built from the fields with each format's own quoting. Set a new value and roll back keep the type. Lists show the type's name, from the content type, without reading a value. A typed value that doesn't match its type exactly (or an unknown type or `v=`) is shown as a plain value with a warning. Field length caps, and Key Vault's 25 KB limit on the encoded JSON with an error naming the field to shorten. Password, key and passphrase fields offer the generator. With `KEYRING_REQUIRE_REASON=all`, the reason page never carries a create or "set a new value" form, so no field is written back into a page. Closes #208.
- **A reason before a value is shown** (#242): optional `KEYRING_REQUIRE_REASON` (`off`, `reveal` or `all`) and `KEYRING_REASON_TICKET_PATTERN` (a regex the ticket must match as a whole, shape only), checked at start, with `requireReason` and `reasonTicketPattern` in both Bicep templates. Keyring asks for a reason (5 to 200 characters) before a reveal or private key download, or before every change with `all`, after the form token and step-up checks and before any Key Vault call. The reason and ticket fill the audit event's `reason` and `ticket` fields, with control characters replaced so neither log format can be forged. New reason code `reason_required` (schema version stays 1). Adds the `regex` crate. Keyring's own check: the CLI needs no reason. Closes #205.
- **Sentinel content for Keyring's audit table** (#243): `infra/sentinel` adds the ASIM Audit Event parser `vimAuditEventKeyring` (and `ASimAuditEventKeyring`) for `KeyringAudit_CL`, seven analytic rules as Sentinel Scheduled rules (many reveals by one person, a reveal from a new address, one person denied in several vaults, a purge, private key download or bulk change (`*.bulk_update`) outside working hours, forged or cross-site requests, no audit events while Key Vault saw Keyring, and a Key Vault `SecretGet` with no Keyring event), hunting queries for the audit page's reports, and a workbook. Every rule is created turned off and turned on by its own parameter, with thresholds and windows as parameters and Account, IP and Azure resource entities. The two rules that need Keyring's outbound addresses aren't created without them, and the `SecretGet` rule stays off until a real vault confirms the `kv_request_id` join. With `KEYRING_AUDIT_WORKSPACE_ID` (set by both templates from `auditWorkspaceId`, checked at start), each vault's audit page gains a **Keyring activity** view of `KeyringAudit_CL`, read as you with your own Log Analytics token, with the same filters, escaping and 500-row limit; without the setting nothing changes. CI builds the template, and `tests/sentinel.rs` checks every column, action, outcome and reason code the content uses against the code. See `docs/sentinel.md`. Closes #224.
- **Change many items at once** (#244): a checkbox on each row of the secrets, certificates and keys lists and a "With selected" form to add or change a tag, remove a tag, set an expiry date (secrets and keys), enable or disable up to 100 items. A review page lists every item and exactly what will change, then a second post changes each as you, four at a time, with a results page per item (done, refused by Keyring or Azure with the role, not found, failed). Disable needs the count typed. Delete and purge stay one at a time. New audit actions `secret.bulk_update`, `certificate.bulk_update` and `key.bulk_update`, written for the request and for each item, and a new reason code, `tag_limit`. The four-at-a-time runner is shared with import (`src/routes/batch.rs`). Closes #216.
- **Pinned and recently opened** (#240): a **Pin** button (a real button with `aria-pressed`) under the heading of each vault list and each secret, certificate and key page, and **Pinned** and **Recently opened** (last 10) above everything else on the home page and vault list, when non-empty. Kept in the browser's `localStorage` under one key, holding only kinds, names and local paths (pinned capped at 50); each entry is checked to be a local `/v/{vault}/...` path before it is a link, or dropped. Signing out clears it, and there's a Clear button. A second same-origin script, `static/pins.js` (under 200 lines, no `innerHTML`, tested); the CSP is unchanged and pages are the same without JavaScript or storage. Closes #220.
- **Import secrets from a file** (#234): "Import secrets" on the secrets list reads a `.env` or CSV file (`name,value`, optional `content_type`, `expires`, `tags`), up to 500 rows and 1 MB, converts names to Key Vault's rules and refuses names that clash, and shows a preview of every name and whether it is new, a new version or blocked by a deleted secret, never a value. Import writes each secret as you, four at a time, with a results page per row. The file waits in the server-side session for up to 10 minutes and is zeroised when dropped. A new audit action, `secret.import`, is written for the request and for each secret written. There is no export. Closes #217.

- **Used by in the last 30 days** (#236): each secret, certificate and key page, and Set a new value, Roll back, Disable, Rotate and Delete, list the people, apps and managed identities that read the secret (or the certificate's backing secret) or signed, wrapped, decrypted and so on with the key, from Key Vault's audit log: kind, name or app ID, object ID, last use, count, client info and IP. ### Security

- `deny.toml` also bans `aws-lc-rs` and `aws-lc-sys`, so a dependency change can't quietly swap rustls's ring provider for aws-lc.
- CI installs its tools only from pinned, checksummed binaries (no fallback download), pins the Bicep CLI, and pins the Dockerfile build frontend by digest.

### Deployment

- Container Apps with `ingress = 'internal'` is reachable from the VNet. The template outputs `defaultDomain` and `staticIp` and can create the private DNS zone (`privateDnsVnetId`).
- Both templates take `apiScope` and `logLevel`.
- App Service can send Keyring's output to Log Analytics (`logAnalyticsWorkspaceId`), and otherwise keeps a 7 day local log.
- The alerts template puts the system topic in the vault's region and can use a topic the vault already has (`existingSystemTopicName`).
- Images carry `org.opencontainers.image.version` and `org.opencontainers.image.revision` labels.
